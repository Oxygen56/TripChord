**把一句旅行愿望，变成一份价格算清、安排完整的出行方案。**

TripChord 是一个帮用户比较和选择自由行程的多 Agent 产品。你只需要说清楚想去哪里、哪段时间方便、准备玩几天、几个人以及在意什么，它就会同时查找已连接的交通、住宿和接驳平台，算清这趟旅行所有人的人民币总费用，最后给出一份最合适的安排。

这里的“最合适”不是让语言模型凭感觉挑一个，也不代表全网绝对最低。系统只比较本次确实查到、航班和房型能够对上、费用口径一致的方案：先保证日期、人数、住宿要求和交通衔接都合适，再优先选择整趟旅行费用更低的方案，同时照顾用户明确说过的品质、位置、早餐、中转等偏好。

TripChord 正从可用原型走向 1.0。现在可以用示例数据完整走通规划，也可以在配置后进行受限的只读实时查询。长时间规划的任务状态和已完成日期结果已经保存到 PostgreSQL；在同一台设备上，API 或 worker 中断后可以继续未完成的部分。要成为可以长期使用的成熟产品，还需要把浏览器采集和短期报价也纳入同一恢复链，并补齐复杂同行人报价、安装升级和持续运行保障。TripChord 不下单、不付款，也不锁定库存。

TripChord 1.0 聚焦交通、住宿和接驳的一体化出行决策，不是逐日景点和餐厅攻略生成器。

## 现在能做到什么

| 状态 | 能力 |
| --- | --- |
| 已实现并持续自动检查 | 灵活日期生成、交通住宿接驳组合、费用计算与检查、多 Agent 协作、偏好记忆、一份最终建议，以及规划任务的幂等提交、取消和同机中断恢复 |
| 已有受限实时连接 | 模型服务、平台 API、官方页面和本机只读浏览器路径；平台登录、页面变化和来源差异仍会影响结果 |
| 走向 1.0 还要完成 | 十分钟内完成最长 21 天的正式支持窗口、统一实时入口、混合同行人真实报价、浏览器采集与报价的跨重启恢复、普通用户安装升级和持续运行保障 |

“已有受限实时连接”不等于现在已经能稳定、反复地完成每一次真实规划。当前版本更适合作为可以继续验证和打磨的开发版本；只有平台、日期、人数和费用都满足正式支持范围时，系统才会给出可供用户决策的最终建议。

## 产品故事

一次真实旅行决策很少只是“找最便宜机票”。例如：

> 我想在 8 月 20 日至 9 月 10 日之间从杭州去马尔代夫，旅行 4–7 天；这次是 2 位成人、1 间房，住宿不能简陋或偏僻，希望兼顾品质和价格。

这句话背后同时存在多个问题：

- 日期窗口会产生大量合法出发与返程组合；
- 最便宜的机票、酒店和接驳未必能组成可行行程；
- 不同平台展示的是单人价、每晚价、起价或含税总价，不能直接比较；
- 住宿位置、房型、早餐、取消规则和交通衔接会影响真实体验；
- 用户希望系统记住稳定偏好，但不能把历史价格当作当前价格。

传统搜索通常把这些决定留给用户逐页完成。TripChord 会把日期、航班、住宿、接驳和费用放在一起考虑：先找出可行的日期，再查询多个平台，把不同写法的报价换算成同一种口径，检查整段行程能不能真正衔接，最后只给用户一份完整安排，而不是把几十条搜索结果重新丢回来。

## 用户最终会得到什么

一份最终方案包含：

- 明确的出发、返程日期和交通班次；
- 对应日期、房型、餐食和取消条件的住宿安排；
- 机场、酒店与目的地之间的接驳；
- 在当前平台支持的同行人组合内，按本次实际人数计算的整趟旅行人民币总费用；
- 为什么选择它，以及预订前仍需确认的条件。

同行人数是每次需求的输入，并非产品固定为“两位成人”。当前来源不支持的儿童、婴儿或房间组合会被明确拒绝，不会套用成人价格。TripChord 只负责查询、比较、校验和建议，不下单、不付款、不锁定库存，也不替用户接受平台条款。

## 一次规划如何完成

```mermaid
flowchart LR
  A[自然语言需求] --> B[需求与偏好]
  B --> C[合法日期搜索空间]
  C --> D[并行查询交通、住宿、接驳]
  D --> E[统一产品与人民币总价]
  E --> F[组合可行行程]
  F --> G[检查必须满足的要求与旅行风险]
  G --> H[必要时修复并重验]
  H --> I[一份最终方案]
```

1. 记下用户不能妥协的日期、人数、房间、预算和旅行要求。
2. 确定性生成全部合法日期组合，并记录本次预算实际覆盖的范围。
3. 用固定工作池查询已连接的交通、住宿和接驳来源。
4. 确认每个报价究竟对应哪个航班、房型或接驳班次，以及适用日期、人数、税费、币种和查询时间。
5. 组合交通、住宿和接驳都能成立的出行方案，排除时间、地点、房间、预算和衔接不成立的候选。
6. 让不同 Agent 各自使用限定的信息、工具和输出格式，完成语义选择、风险检查和必要修复。
7. 由确定性系统重新校验，并只发布一份最终方案。

## 项目亮点

### 1. 把灵活日期当成搜索空间，而不是一句模糊描述

TripChord 会展开日期窗口内的合法组合。全部日期由程序生成，模型不能为了省事改写搜索范围；系统再用固定数量的后台任务、每个平台自己的访问上限和重复查询合并来控制耗时。只有实际查完整个日期范围，系统才会声称完成了完整比较。

### 2. 算整趟旅行要花多少钱，而不是只看页面上最小的数字

TripChord 会先确认报价适用于几个人、几间房、哪些日期、哪个具体航班或房型，是否含税，以及查询发生在什么时候。只有能算清整趟旅行所有人实际支出的人民币费用，方案才会参加最终比较；缺少税费、只有单人起价或对不上具体产品时，该报价不会参加最终比较。系统会说明缺口，并在补查能力可用时重新查询，而不会把它包装成最便宜。

### 3. Multi-Agent 负责专业判断，确定性系统负责事实

语言模型处理需求歧义、偏好取舍、价格含义、旅行风险和变化影响；金额、日期、权限、具体航班与房型、当前有效性、修复执行和最终检查始终由程序负责。模型拥有真实决策空间，但没有篡改事实的权限。

### 4. 长任务可以并行、去重，并从中断处继续

当前版本已经能在一次运行中合并相同查询、显示进度并处理取消；不同平台按照各自节奏运行，某个平台失败不会被伪装成“没有库存”。规划任务的状态、已完成的日期结果、租约和取消状态保存在 PostgreSQL；进程强制终止后，新进程只会继续未完成的日期，旧进程的迟到结果不能覆盖新结果。这条恢复链目前只在同一台设备内成立，并且尚未包含浏览器采集任务和短期报价复用；这两部分是 1.0 前要继续统一的可靠性边界。

### 5. 记住用户偏好，但不记住过期价格

用户确认的早餐、行李和中转等稳定偏好可以按作用域保存、撤销和过期。本次明确需求总是优先；价格、库存、余位、班次和可订状态永远不会作为长期偏好进入下一次规划。

### 6. 只向用户发布一个答案

系统内部可以保留备选方案和淘汰原因，但用户最终只会看到一份建议行程。如果费用没有算清、关键平台没有返回结果，或者行程不满足用户不能妥协的要求，TripChord 会直接说明目前还缺什么、为什么暂时不能给出可靠答案，而不会拿一串半成品让用户自己收拾。

## 为什么采用 Multi-Agent

TripChord 的 Multi-Agent 不是按日期复制一群聊天机器人，而是让不同角色负责不同判断，并限制它们分别能看到什么、能使用什么工具。当前核心规划仍把大多数审查和修复职责放在固定任务图中，另外一些职责只在灵活日期、变化处理或发布路径中出现。下表是一张职责清单，不等于每次运行的模型调用次数；1.0 会通过对照评测决定哪些角色保持常驻、延后执行或改为条件触发，而不是用角色数量证明先进性。

| 专业 Agent | 专门负责 | 为什么保持独立 |
| --- | --- | --- |
| `Context` | 将自然语言需求转换为结构化条件与偏好候选 | 用户事实是后续所有步骤的根，不能被搜索结果反向改写 |
| `Query Strategist` | 在已经确认的日期范围与查询预算内提出精查顺序 | 搜索覆盖问题与“选哪份行程”是不同决策 |
| `Search Supervisor` | 根据来源能力、任务依赖和限额安排查询波次 | 只看允许执行的任务 ID，不能改变用户条件或平台权限 |
| `Evidence Arbiter` | 判断不同来源的产品和价格是否可比 | 在偏好选择前先建立统一事实口径，避免规划者给喜欢的候选补事实 |
| `Candidate Curator` | 在可行候选中结合总价与明确偏好提出首选 | 可以做语义取舍，但不能创造报价或修改验证结果 |
| `Risk Critic` | 独立检查中转、入住、位置和接驳等软风险 | 不继承策展者的选择理由，减少对首选方案的锚定 |
| `Repair Strategist` | 根据失败原因提出在现有候选中的有限调整 | 当前只执行已核对候选内的程序化修改；扩大搜索或询问会成为后续动作 |
| `ReCritic` | 复查修复后的新候选是否引入其他风险 | 修复者不能同时给自己的修改做最终软风险验收 |
| `Event Diagnoser` | 判断输入的价格、班次或库存变化事件影响哪些组件 | 将局部影响识别与整份行程重新规划分开；当前不宣称已接入供应商实时推送 |
| `Orchestrator` | 汇总各角色的结构化意见并提出业务状态建议 | 不直接发布结果，后面仍有确定性安全门 |
| `Explanation` | 从已绑定的事实声明中组织用户可读解释 | 可以改变表达顺序，不能新增产品事实 |
| `Memory Curator` | 提出待用户确认的稳定偏好候选 | 规划结果和长期记忆分离，模型不能直接写入用户画像 |

与这些 Agent 并行存在的，还有不能由语言模型替代的程序组件：日期生成、平台查询、报价统一、行程组合、规则检查、修复执行、修复后复查和最终安全检查。它们共同保证任何一个模型都不能独自决定价格、授权和最终结果。

## 关键技术取舍

| 问题 | TripChord 的选择 | 放弃了什么 |
| --- | --- | --- |
| 完整日期 vs. 热门日期抽样 | 程序生成全部合法日期，再用固定工作池和重复查询合并控制耗时 | 不让模型为了速度随意漏日期 |
| 并发速度 vs. 平台稳定性 | 日期、来源和模型分层并行，每个平台保留独立并发与启动间隔 | 不用无限并发制造更快的假象 |
| 结果复用 vs. 价格新鲜度 | 探索阶段让相同查询共享一次采集；给出最终方案前重新查询其中的关键部分 | 不把历史结果直接当作当前价格 |
| LLM 灵活性 vs. 可验证性 | 模型只输出结构化提案，事实与发布门由确定性代码控制 | 不允许模型用自然语言绕过失败码 |
| 个性化 vs. 实时事实污染 | 长期记忆只保存经确认的稳定偏好 | 不把价格、库存和班次写入 RAG |
| 通用框架 vs. 领域控制 | 保留类型化自研运行时，按明确触发条件评估 LangGraph/Temporal | 不为框架标签重写已有安全合同 |

### 为什么没有直接迁移到 LangGraph

TripChord 已经拥有类型化任务图、依赖校验、并发、重试、动态任务准入、工具权限和审计回执。LangGraph 的检查点、暂停恢复和状态调试很有价值，但不能替代浏览器租约、报价新鲜度、平台限流、金额校验和最终发布门。

当前选择是：领域安全内核继续由 TripChord 控制；规划任务和已完成日期结果已经使用 PostgreSQL 持久化，下一步是把浏览器采集和报价复用纳入同一控制面。只有模型子流程真实需要跨重启暂停恢复或复杂循环时，才通过隔离适配器评估 LangGraph。若未来需要跨机器、小时级可靠执行，再评估 Temporal 这类持久工作流，而不是把 Agent 框架当成业务队列。

## 技术结构

```text
apps/api/src/tripchord/   FastAPI、领域模型、Agent 运行时与来源适配器
apps/web/                 React 用户界面
apps/browser-companion/   本机只读浏览器连接
apps/api/tests/           API、规划、记忆与来源测试
benchmarks/               日期搜索、并发、恢复与 Agent 对照基准
docs/                     架构、来源、上下文、运行与面试说明
scripts/                  启动、回放、检查与维护工具
```

核心技术包括 Python 3.12+、FastAPI、Pydantic、SQLAlchemy、PostgreSQL、Redis、OR-Tools、React 19，以及一个受限的本机 Chrome Companion。PostgreSQL 任务恢复已经通过本机真实 PostgreSQL 17 集成测试，CI 也会运行同一类数据库检查。当前快速开始仍是面向开发者的本地配置，不代表整个产品已经封装为成熟的多进程应用；1.0 会把本地数据库、后台任务、升级和恢复一起封装进安装包。

## 快速开始

需要 Python 3.12 或 3.13、Node.js 22 和 [uv](https://docs.astral.sh/uv/)。

```bash
git clone --branch productization/v1.0 https://github.com/Oxygen56/TripChord.git
cd TripChord
uv sync --locked --all-groups
npm ci
uv run alembic upgrade head
```

启动 API：

```bash
uv run uvicorn tripchord.main:app --app-dir apps/api/src --reload
```

另开终端启动前端：

```bash
npm run dev
```

访问 `http://localhost:5173`，API 文档位于 `http://localhost:8000/docs`。

默认配置使用本地回放数据，并关闭外部模型调用（`MODEL_PROVIDER=none`）。复制并编辑 [`.env.example`](.env.example) 可以启用兼容 OpenAI Chat Completions 的模型服务、供应商 API 或本机浏览器连接。

实时网页查询需要用户在自己的 Chrome 中登录对应平台，并为 [Chrome Companion](apps/browser-companion/README.md) 授予指定域名的只读权限。TripChord 不读取 Cookie、密码或 Chrome 用户目录，也不会把浏览器连接密钥发送给模型。

## TripChord 最终会成为怎样的产品

成熟的 TripChord 不是一个旅行搜索结果聚合页，而是一位真正替用户把比较工作做完的旅行决策助手：用户说一次需求，系统完成跨日期、跨平台、跨交通与住宿的组合搜索，记住经过确认的长期偏好，算清所有人的整趟旅行费用，并交付一份包含去程、返程、住宿、接驳、费用明细、选择理由和官方查看入口的最终安排。用户想改得更便宜、更舒适或更少中转时，系统会重新计算，并继续只给一份更新后的建议。

完整建设从当前最影响体验的等待时间开始：先优化内部并行、重复查询和模型调用，再依次补齐任务中断恢复、人数和价格口径、平台覆盖、规划质量、用户体验与正式发布。

| 阶段 | 用户真正得到的变化 |
| --- | --- |
| 当前基线 | 核心规划链、灵活日期、跨平台比较、多 Agent 协作、偏好记忆和只读浏览器能力已经形成 |
| Beta | 在明确支持的目的地、平台和同行人范围内，普通用户可以从统一入口稳定完成真实规划；中断后能够继续，耗时与失败原因看得懂 |
| RC | 多进程运行、取消、重试、恢复、平台变化和安全边界经过持续故障测试；同一需求能够重复形成可靠的一份最终方案 |
| 1.0 | 用户可以独立安装、升级、回滚和清除数据；支持范围、性能目标、隐私规则和长期维护方式稳定 |

完整的产品形态、九个建设阶段、每阶段的用户结果与完成标准见 [TripChord 1.0 产品蓝图与完整迭代路线](docs/roadmap.md)。项目不会为了升级版本号而放松价格和行程检查，也不会把示例数据、模型已经接入或页面能打开说成真实库存与成交能力。

## 当前边界

- 只比较本次实际查到且可以公平比较的平台，不宣称全网最低。
- 部分平台或复杂成人、儿童、婴儿组合尚未具备完整报价能力。
- 平台登录、验证码、网络和网页结构变化可能阻断实时查询。
- 不自动下单、支付、接受条款、锁库存、修改或取消预订。
