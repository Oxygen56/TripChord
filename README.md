# TripChord（旅弦）

**在灵活日期和多个来源之间，组合一份满足出行要求、总价口径完整的最佳行程。**

TripChord 是一个面向自由行的多 Agent 规划系统。用户可以给出出发地、目的地、灵活日期范围、旅行时长、同行人数和出行偏好，TripChord 会组合交通、住宿与接驳，在满足硬条件的方案中比较完整的人民币同行总价，最终只交付一份建议行程。

它解决的不是“生成一段旅游文案”，而是一个带实时数据和多重约束的组合决策问题：日期会改变票价和房价，最便宜的单项未必能安全衔接，不同平台的价格口径也不能直接相加。

## 用户会得到什么

一份最终方案包含：

- 明确的出发、返程日期和交通班次；
- 对应入住日期、房型、餐食与取消条件的住宿安排；
- 机场、酒店和目的地之间的接驳；
- 按实际同行人数计算的人民币总价；
- 选择该方案的原因，以及仍需在预订前确认的条件。

在成功覆盖且口径可比的候选中，TripChord 把完整人民币同行总价作为首要排序依据；用户明确设置的加权偏好可以在同一可比层级内参与取舍。

TripChord 只负责查询、比较、校验和建议，不下单、不付款、不锁定库存，也不替用户接受平台条款。

## 工作流程

```mermaid
flowchart LR
  A[自然语言需求] --> B[结构化需求与偏好]
  B --> C[合法日期组合]
  C --> D[并行查询交通、住宿和接驳]
  D --> E[统一价格与产品口径]
  E --> F[组合候选行程]
  F --> G[硬约束校验]
  G --> H[风险审查与必要修复]
  H --> I[一份最终方案]
```

1. 理解用户需求，并区分硬约束、软偏好和缺失信息。
2. 根据日期范围与旅行时长生成全部合法日期组合。
3. 以固定并发查询已连接的交通、住宿和接驳来源。
4. 将不同来源的报价统一为相同日期、产品、人数、税费和币种口径。
5. 组合完整行程，排除日期、人数、房间、地点和衔接不成立的候选。
6. 对首选候选进行独立风险审查；需要修复时，只重查受影响的部分。
7. 重新校验整份行程，发布唯一的最终方案。

## 为什么使用多 Agent

旅行规划同时包含语言理解、搜索策略、来源判断、组合优化和风险审查。把这些工作全部交给同一个模型，会让事实、偏好与最终取舍混在同一段上下文中，也很难阻止模型用推测补齐缺失价格。

TripChord 将模型职责拆开，并为每个角色提供独立、受预算限制的上下文：

| 模型角色 | 职责 |
| --- | --- |
| 需求理解（`Context`） | 将自然语言转换为日期、人数、房间、预算、硬约束和偏好 |
| 查询策略（`Query Strategist`） | 规划灵活日期搜索范围和查询优先级 |
| 搜索监督（`Search Supervisor`） | 在既定权限和预算内调整来源查询顺序 |
| 数据仲裁（`Evidence Arbiter`） | 排除与查询条件、产品身份或价格口径不一致的来源结果 |
| 候选策展（`Candidate Curator`） | 比较可行候选并提出首选行程 |
| 风险审查（`Risk Critic`） | 独立检查中转、入住、接驳和位置等软风险 |
| 修复策略（`Repair Strategist`） | 在失败或变化后提出最小替换与补查范围 |
| 修复复审（`ReCritic`） | 检查修复是否引入新的风险 |
| 事件诊断（`Event Diagnoser`） | 判断价格、班次、库存等变化影响了哪些组件 |
| 主控建议（`Orchestrator`） | 汇总各角色意见，但不直接越过发布条件 |
| 解释与记忆（`Explanation` / `Memory Curator`） | 生成用户可读解释，并提出待确认的稳定偏好 |

多 Agent 并不意味着“每个日期启动一组模型”。日期枚举、平台查询和报价处理使用固定数量的工作单元；模型角色主要用于最终候选的语义判断和风险审查，因此日期范围扩大时不会无控制地复制模型调用。

## 确定性系统拥有最终决定权

模型可以理解需求、提出候选和发现风险，但不能决定关键事实。以下部分由确定性代码负责：

- 日期与晚数计算；
- 来源权限、只读动作和调用预算；
- 查询去重、超时、取消和重试；
- 产品身份、人数、房间、币种、税费和总价归一；
- 航段、入住、接驳和地点衔接校验；
- 候选生成、完整人民币总价排序与预算检查；
- 修复执行、重新校验和最终发布。

这种分工让 LLM 负责它擅长的开放式判断，让程序负责必须精确、可重复的计算和约束。

## 灵活日期搜索与性能设计

“在某个日期范围内出发，旅行若干天”会产生大量日期组合。TripChord 先确定性生成完整日期集合，再通过固定工作池并行执行，而不是按日期串行规划。

为了减少重复工作，系统为每个查询生成包含来源、路线、日期、同行人数、房间、币种和住宿计划的指纹。同一次运行中，相同指纹共享同一个进行中或已完成的结果，包括明确的失败结果；最终发布前的价格刷新则会主动绕过缓存。

在覆盖 66 个日期组合的集成基准中：

- 858 个逻辑查询合并为 648 个实际查询；
- 210 个跨日期重复查询被消除；
- 3 个固定日期工作单元并行运行；
- 最后一项查询的计划启动时间为 290 秒，保守完整运行预算为 530 秒。

这些优化完全发生在 TripChord 内部，不要求旅行平台提供批量查询接口。实际平台阶段的耗时仍取决于网络、登录状态和页面响应。

## 价格如何比较

TripChord 不直接比较页面上看起来最小的数字。一个报价必须先绑定到确切的日期、同行人数、产品和采集时间，再进入行程组合。

最终价格排序只接受完整的人民币同行总价。缺少税费、只提供单人价、包含未换算外币小计、产品身份不明确或已经过期的报价，可以作为补查线索，但不会被发布为“最便宜方案”。

当多个平台成功返回相同口径的产品时，系统在这些来源之间比较；某个平台登录失效、出现验证码或页面发生变化时，不会被静默当成“没有更低价格”。

## 上下文与偏好记忆

不同模型角色只接收完成自己任务所需的上下文。当前请求和本次查询结果优先，历史信息经过作用域、有效期和大小限制后才能进入模型；风险审查角色不会直接继承规划角色的选择理由。

TripChord 可以记住用户明确确认、相对稳定的偏好，例如是否需要早餐、托运行李，以及是否接受中转。这些偏好支持撤销和过期，本次请求中的明确要求始终优先。

实时价格、库存、余位、班次和可订状态不会写入长期记忆，也不会从历史偏好中恢复。发布最终方案前，TripChord 会强制刷新选中的组件并重新校验，避免旧报价污染新行程。

## 变化与重新规划

价格、班次或库存发生变化时，TripChord 先定位受影响的组件，再重查相关来源、选择替代项并重新校验整份行程。没有变化的航班、住宿或接驳会尽量保留，避免从头执行所有搜索。

如果局部修复无法继续满足日期、总价或衔接条件，系统会升级为全局重查；仍然无法形成可靠方案时，会明确说明缺少什么信息，并停止发布已经失效的结果。

## 快速开始

需要 Python 3.12 或 3.13、Node.js 22 和 [uv](https://docs.astral.sh/uv/)。

```bash
git clone --branch productization/v1.0 https://github.com/Oxygen56/TripChord.git
cd TripChord
uv sync --locked --all-groups
npm ci
uv run alembic upgrade head
```

启动 API：

```bash
uv run uvicorn tripchord.main:app --app-dir apps/api/src --reload
```

另开终端启动前端：

```bash
npm run dev
```

访问 `http://localhost:5173`，API 文档位于 `http://localhost:8000/docs`。

默认配置使用本地回放数据，并关闭外部模型调用（`MODEL_PROVIDER=none`）。复制并编辑 [`.env.example`](.env.example) 可以启用兼容 OpenAI Chat Completions 的模型服务、供应商 API 或本机浏览器连接。

实时网页查询需要用户在自己的 Chrome 中登录对应平台，并为 [Chrome Companion](apps/browser-companion/README.md) 授予指定域名的只读权限。TripChord 不会把 Cookie、登录凭据、Chrome 用户目录或连接密钥发送给模型。

```text
apps/api/src/tripchord/   FastAPI、领域模型、Agent 运行时与来源适配器

apps/api/tests/           API、规划、记忆与来源测试

```

## 项目阶段

TripChord 目前处于早期开发阶段（Alpha）。核心规划运行时、灵活日期搜索、跨日期去重、完整人民币同行总价、偏好记忆、变化重规划和只读浏览器连接均已实现；不同平台的可访问性仍会受到账号状态、验证码、网络和网页结构变化影响。

部分平台或复杂同行人组合尚未提供完整报价能力。遇到无法可靠计算的情况，TripChord 会停止发布最终方案并说明缺失条件，而不是猜测价格或库存。
