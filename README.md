**把一句旅行愿望，变成一份可以直接做决定的最佳行程。**

TripChord 是一个面向自由行的多 Agent 规划系统。它接收出发地、目的地、灵活日期、旅行时长、同行人数和偏好，搜索已连接的交通、住宿与接驳来源，在来源明确支持的人数和房间组合内统一比较完整的人民币同行总价，最后只交付一份满足要求的建议行程。

这里的“最佳”不是凭语言模型感觉生成，也不代表全网绝对最低，而是：**在本次成功获取、身份明确且价格口径可比的方案中，先满足所有硬条件，再以完整人民币同行总价为首要依据，结合用户明确偏好做最终选择。**

当前版本为 Alpha：开箱默认使用示例数据；配置模型服务与来源连接后，可以进行受控的只读实时查询。标准实时入口、复杂同行人覆盖和跨重启恢复仍在完善；下单、支付和库存锁定不在产品范围内。

## 产品故事

一次真实旅行决策很少只是“找最便宜机票”。例如：

> 我想在 8 月 20 日至 9 月 10 日之间从杭州出发，旅行 4–7 天；这次是 2 位成人、1 间房，住宿不能简陋或偏僻，希望兼顾品质和价格。

这句话背后同时存在多个问题：

- 日期窗口会产生大量合法出发与返程组合；
- 最便宜的机票、酒店和接驳未必能组成可行行程；
- 不同平台展示的是单人价、每晚价、起价或含税总价，不能直接比较；
- 住宿位置、房型、早餐、取消规则和交通衔接会影响真实体验；
- 用户希望系统记住稳定偏好，但不能把历史价格当作当前价格。

传统搜索通常把这些决定留给用户逐页完成。TripChord 把它们建模为一个完整的约束规划问题：先展开合法日期，查询多个来源，再统一产品和价格口径，组合候选、检查风险，最终返回一份完整行程，而不是把几十条搜索结果重新丢给用户。

## 用户最终会得到什么

一份最终方案包含：

- 明确的出发、返程日期和交通班次；
- 对应日期、房型、餐食和取消条件的住宿安排；
- 机场、酒店与目的地之间的接驳；
- 在当前来源支持的同行人组合内，按本次实际人数计算的人民币总价；
- 为什么选择它，以及预订前仍需确认的条件。

同行人数是每次需求的输入，并非产品固定为“两位成人”。当前来源不支持的儿童、婴儿或房间组合会被明确拒绝，不会套用成人价格。TripChord 只负责查询、比较、校验和建议，不下单、不付款、不锁定库存，也不替用户接受平台条款。

## 一次规划如何完成

```mermaid
flowchart LR
  A[自然语言需求] --> B[需求与偏好]
  B --> C[合法日期搜索空间]
  C --> D[并行查询交通、住宿、接驳]
  D --> E[统一产品与人民币总价]
  E --> F[组合可行行程]
  F --> G[硬约束与风险审查]
  G --> H[必要时修复并重验]
  H --> I[一份最终方案]
```

1. 冻结用户明确提出的日期、人数、房间、预算和硬条件。
2. 确定性生成全部合法日期组合，并记录本次预算实际覆盖的范围。
3. 用固定工作池查询已连接的交通、住宿和接驳来源。
4. 将报价绑定到确切产品、日期、人数、税费、币种和采集时间。
5. 组合完整行程，排除时间、地点、房间、预算和衔接不成立的候选。
6. 让上下文、工具和输出合同逻辑隔离的 Agent 完成语义选择、风险审查和必要修复。
7. 由确定性系统重新校验，并只发布一份最终方案。

## 项目亮点

### 1. 把灵活日期当成搜索空间，而不是一句模糊描述

TripChord 会展开日期窗口内的合法组合。日期全集由程序生成，模型不能为了省事改写搜索范围；执行阶段使用固定 worker、来源级并发限制和跨日期去重。只有查询预算实际覆盖全集时，系统才能声称完成了全窗口比较，否则必须明确标记为未穷尽。

### 2. 比较完整同行总价，而不是页面上最小的数字

报价必须先绑定人数、房间、日期、产品身份、税费、币种和采集时间。只有完整、可比的人民币同行总价才能进入最终价格排序；缺失税费、只给单人价或身份不明确的报价只能触发补查，不能被包装成最低价。

### 3. Multi-Agent 负责专业判断，确定性系统负责事实

LLM 处理语言歧义、偏好取舍、价格语义、软风险和变化影响；金额、日期、权限、产品身份、新鲜度、修复执行与最终发布始终由可复算代码负责。模型拥有真实决策空间，但没有篡改事实的权限。

### 4. 长任务可以并行、去重，并保留清晰的恢复边界

相同查询会共享一次执行和同一类型化结果；平台查询按照独立节奏运行，某个来源失败不会被伪装成“没有库存”。系统记录阶段状态、失败原因和受影响组件，为重试、取消和后续持久化恢复提供明确边界。

### 5. 记住用户偏好，但不记住过期价格

用户确认的早餐、行李和中转等稳定偏好可以按作用域保存、撤销和过期。本次明确需求总是优先；价格、库存、余位、班次和可订状态永远不会作为长期偏好进入下一次规划。

### 6. 只向用户发布一个答案

内部可以保留候选、被拒原因和排序诊断；证据完整时，面向用户的最终投影只有一份 `FinalPlan`。完整总价、必要来源或硬条件不成立时，TripChord 输出零方案和明确缺口，不会用候选列表或猜测掩盖失败。

## 为什么采用 Multi-Agent

TripChord 的 Multi-Agent 不是按日期复制一群聊天机器人，而是把不同判断放进逻辑隔离的上下文、工具权限和失败边界。这些角色共享模型路由和进程，仍存在共同故障域；下表说明的是当前角色拆分的**设计理由**，而不是用角色数量证明先进性。角色对质量、成本和延迟的边际贡献仍应通过持续评测验证。

| 模型角色 | 专门负责 | 为什么保持独立 |
| --- | --- | --- |
| `Context` | 将自然语言需求转换为结构化条件与偏好候选 | 用户事实是后续所有步骤的根，不能被搜索结果反向改写 |
| `Query Strategist` | 在冻结日期空间与预算内提出精查顺序 | 搜索覆盖问题与“选哪份行程”是不同决策 |
| `Search Supervisor` | 根据来源能力、任务依赖和限额安排查询波次 | 只看允许执行的任务 ID，不能改变用户条件或平台权限 |
| `Evidence Arbiter` | 判断不同来源的产品和价格是否可比 | 在偏好选择前先建立统一事实口径，避免规划者给喜欢的候选补事实 |
| `Candidate Curator` | 在可行候选中结合总价与明确偏好提出首选 | 可以做语义取舍，但不能创造报价或修改验证结果 |
| `Risk Critic` | 独立检查中转、入住、位置和接驳等软风险 | 不继承策展者的选择理由，减少对首选方案的锚定 |
| `Repair Strategist` | 根据失败码与冻结候选提出换选、补查或询问 | 只提出有界修复，实际修改仍由确定性执行器完成 |
| `ReCritic` | 复查修复后的新候选是否引入其他风险 | 修复者不能同时给自己的修改做最终软风险验收 |
| `Event Diagnoser` | 判断输入的价格、班次或库存变化事件影响哪些组件 | 将局部影响识别与整份行程重新规划分开；当前不宣称已接入供应商实时推送 |
| `Orchestrator` | 汇总各角色的结构化意见并提出业务状态建议 | 不直接发布结果，后面仍有确定性安全门 |
| `Explanation` | 从已绑定的事实声明中组织用户可读解释 | 可以改变表达顺序，不能新增产品事实 |
| `Memory Curator` | 提出待用户确认的稳定偏好候选 | 规划结果和长期记忆分离，模型不能直接写入用户画像 |

与这些模型角色并行存在的，还有不能由 LLM 替代的确定性组件：日期枚举器、Source workers、报价归一器、候选生成器、Hard Verifier、Repair Executor、独立 ReVerifier 和 Safety Gate。它们共同保证任何一个模型都不能独自决定价格、授权和最终发布。

## 关键技术取舍

| 问题 | TripChord 的选择 | 放弃了什么 |
| --- | --- | --- |
| 完整日期 vs. 热门日期抽样 | 确定性生成合法全集，再用固定 worker 和去重控制成本 | 不让模型为了速度随意漏日期 |
| 并发速度 vs. 平台稳定性 | 日期、来源和模型分层并行，每个平台保留独立并发与启动间隔 | 不用无限并发制造更快的假象 |
| 结果复用 vs. 价格新鲜度 | 探索阶段 singleflight；最终发布前强制刷新选中组件 | 不把历史命中直接当作当前价格 |
| LLM 灵活性 vs. 可验证性 | 模型只输出结构化提案，事实与发布门由确定性代码控制 | 不允许模型用自然语言绕过失败码 |
| 个性化 vs. 实时事实污染 | 长期记忆只保存经确认的稳定偏好 | 不把价格、库存和班次写入 RAG |
| 通用框架 vs. 领域控制 | 保留类型化自研运行时，按明确触发条件评估 LangGraph/Temporal | 不为框架标签重写已有安全合同 |

### 为什么没有直接迁移到 LangGraph

TripChord 已经拥有类型化任务图、依赖校验、并发、重试、动态任务准入、工具权限和审计回执。LangGraph 的检查点、暂停恢复和状态调试很有价值，但不能替代浏览器租约、报价新鲜度、平台限流、金额校验和最终发布门。

当前选择是：领域安全内核继续由 TripChord 控制；下一阶段先用 PostgreSQL 统一长任务持久化；只有模型子流程真实需要跨重启暂停恢复或复杂循环时，才通过隔离适配器评估 LangGraph。若未来需要跨机器、小时级可靠执行，再评估 Temporal 这类持久工作流，而不是把 Agent 框架当成业务队列。

## 技术结构

```text
apps/api/src/tripchord/   FastAPI、领域模型、Agent 运行时与来源适配器
apps/web/                 React 用户界面
apps/browser-companion/   本机只读浏览器连接
apps/api/tests/           API、规划、记忆与来源测试
benchmarks/               日期搜索、并发、恢复与 Agent 对照基准
docs/                     架构、来源、上下文、运行与面试说明
scripts/                  启动、回放、检查与维护工具
```

核心技术包括 Python 3.12+、FastAPI、Pydantic、SQLAlchemy、PostgreSQL、Redis、OR-Tools、React 19，以及一个受限的本机 Chrome Companion。

## 快速开始

需要 Python 3.12 或 3.13、Node.js 22 和 [uv](https://docs.astral.sh/uv/)。

```bash
git clone --branch productization/v1.0 https://github.com/Oxygen56/TripChord.git
cd TripChord
uv sync --locked --all-groups
npm ci
uv run alembic upgrade head
```

启动 API：

```bash
uv run uvicorn tripchord.main:app --app-dir apps/api/src --reload
```

另开终端启动前端：

```bash
npm run dev
```

访问 `http://localhost:5173`，API 文档位于 `http://localhost:8000/docs`。

默认配置使用本地回放数据，并关闭外部模型调用（`MODEL_PROVIDER=none`）。复制并编辑 [`.env.example`](.env.example) 可以启用兼容 OpenAI Chat Completions 的模型服务、供应商 API 或本机浏览器连接。

实时网页查询需要用户在自己的 Chrome 中登录对应平台，并为 [Chrome Companion](apps/browser-companion/README.md) 授予指定域名的只读权限。TripChord 不读取 Cookie、密码或 Chrome 用户目录，也不会把浏览器连接密钥发送给模型。

## 从 Alpha 到成熟版本

TripChord 当前处于 Alpha：核心规划、灵活日期、跨来源比较、人民币同行总价、偏好记忆、变化处理和只读浏览器能力已经形成，但标准实时入口、持久化任务控制面、复杂同行人和稳定来源覆盖仍在完善。

成熟度不由版本名称或 Agent 数量决定，而由下面的结果决定：

| 阶段 | 成功标准 |
| --- | --- |
| Beta | 限定支持范围内，标准入口可以稳定完成真实规划；任务重启后可查询和恢复；关键耗时与失败原因可观测 |
| RC | 多进程任务、幂等、取消、恢复和来源覆盖经过故障测试；当前版本可以重复形成唯一最终方案 |
| 1.0 | 有可安装、升级、回滚的不可变发布物；支持范围、SLO、安全边界和迁移策略稳定 |

当前不会为了升级版本号而降低价格、来源和硬约束门槛，也不会把测试数据、模型接线或页面可达误写成真实库存与成交能力。

## 当前边界

- 只比较本次成功覆盖、口径可比的已连接来源，不宣称全网最低。
- 部分平台或复杂成人、儿童、婴儿组合尚未具备完整报价能力。
- 平台登录、验证码、网络和网页结构变化可能阻断实时查询。
- 不自动下单、支付、接受条款、锁库存、修改或取消预订。
