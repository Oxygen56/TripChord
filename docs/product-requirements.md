## 1. 产品目标

TripChord 要让旅行者只用自然语言说明想去哪里、哪些时间方便、和谁同行、有哪些固定安排、预算和在意的体验，就能获得一份真正可以用来做决定的完整行程。

这份行程必须同时回答：

- 每位同行者什么时候从哪里出发、在哪里汇合、什么时候返程；
- 具体乘坐什么交通、住什么酒店、参加什么活动；
- 所有时间和地点能否衔接；
- 这趟旅行总共需要多少钱，价格覆盖哪些人和哪些组件；
- 本次实际比较了哪些日期与来源；
- 为什么这是更适合当前用户的一份方案；
- 每个交通、住宿和活动可以去哪里继续查看或购买。

### “最佳方案”的准确含义

TripChord 所说的“最佳”只在**本次成功取得、费用口径完整且能够公平比较的候选范围内**成立：

- 用户已经表达清楚取舍时，只给一份最符合本次偏好的最终方案；
- 用户没有提供足够偏好时，先给省钱、均衡和体验优先三个代表方案；用户选择或补充偏好后，再收敛为一份最终方案；
- “最便宜”指本次明确披露的比较范围内，满足用户要求后整趟人民币总费用更低，不表示全网最低；
- 价格、库存、税费或关键时间仍不完整时，系统说明缺少什么，不把候选包装成可直接决策的最终方案。

### 空胜利

下面这些都不能单独算产品完成：

- 新增旅行合同、图、求解器、Agent、Skill、插件或平台适配器；
- 内部测试通过、代码量增加或架构图更完整；
- 模型成功返回一段合理文字；
- 保存数据回放成功，但正式入口没有给用户完整行程卡；
- 页面更漂亮，但返程、人数、总费用或来源范围仍不清楚；
- 查询了一部分日期，却把结果写成整个窗口的最低价。

## 2. 2.0 当前状态与准确边界

### 七轮已经具备

- 中文需求进入灵活日期规划主链；
- 单一出发地、单一目的地的机票、住宿和接驳组合；
- 来源记录、人民币换算、产品身份和同行人数检查；
- 保存偏好、撤销偏好和当前请求覆盖历史偏好；
- 自然语言修改、未受影响部分保留和失败后保留原方案；
- 查询任务并行、进度、取消、保存来源回放和最终程序核对；
- 当前正式界面与 API 入口；
- 多城市、固定活动、分地出发/汇合/分流与共享费用的统一旅行图；
- 同一次来源查询上的 Pareto 代表方案、三角色 Multi-Agent 面板、条件 Skill 和确认偏好记忆；
- 版本化 TripRun、局部变化重规划、新交通/在线活动，以及四个粗粒度 MCP 能力。

### 2.0 仍然明确保留的边界

1. 价格、库存、税费或关键时间不完整时，结果会保持 candidate/source_gap；历史马尔代夫运行不能写成今天的可订最低价；
2. 当前来源只覆盖证据文件中列出的平台、目的地和交通类型，未查询来源不能被解释成无库存；
3. 当前活动、轮渡等外币或税费未闭合项目只能作为明确标注的参考候选，不能冒充锁价；
4. 脚本化 Agent 对照只证明预设场景的路由和成本差异，不证明 Multi-Agent 普遍更准确；
5. 仍不提供付款、下单、锁库存、改签、取消、生产 SLA 或所有宿主接入。

## 3. 目标用户与典型需求

| 用户 | 典型需求 |
| --- | --- |
| 单人、情侣或朋友 | 日期灵活，希望在价格、时间和住宿体验之间找到更适合的方案 |
| 亲子家庭 | 儿童年龄、房间、餐食、活动适用性和作息需要一起考虑 |
| 与长辈同行 | 少换乘、少步行、避免红眼、住宿位置方便等条件更重要 |
| 多城市旅行者 | 多个城市、异地进出、固定演出或会议，交通和住宿必须连续 |
| 分地出发的多人团队 | 从不同城市出发，中途汇合、分开活动、部分人提前返程 |
| 已经拿到方案的用户 | 想保留部分安排，只修改酒店、日期、同行者或活动 |
| 其他 Agent 或聊天应用用户 | 从外部宿主创建、等待、读取和继续修改同一个 TripChord 任务 |

## 4. 产品原则

1. **最终答案优先。** 每轮必须改善用户实际拿到的行程，而不是单独交付内部模块。
2. **先把旅行算对，再让模型做取舍。** 日期、金额、人数、容量、地点连续性和最终发布由程序负责。
3. **一轮查询，多种选择。** 省钱、均衡、体验和个性化答案复用同一批来源，不重复搜索。
4. **真实范围透明。** 每个日期和来源都有成功、无结果、失败或被证明无需继续查询的状态，不能静默抽样。
5. **当前请求优先。** 历史偏好只能辅助当前旅行，不能覆盖用户这次明确说的话。
6. **修改尽量少影响。** 用户要求保留的组件以及不受影响的组件默认不变，修改后仍完整复算整趟行程。
7. **并行任务不等于 Multi-Agent。** 日期、平台和候选是普通工作项；只有歧义、冲突、取舍和特殊旅行判断才调用专业 Agent。
8. **只做决策，不做交易。** TripChord 不下单、付款、锁定库存、接受条款、修改或取消预订。

## 5. 完整功能要求

### PR-01 自然语言旅行需求

系统应理解并形成可检查的旅行需求：

- 一位或多位同行者及其年龄类别；
- 每个人的出发地、可出行时间和参与范围；
- 单一或多个目的地、异地进出和候选地点；
- 最早出发、最晚结束、旅行天数范围；
- 演唱会、会议、固定入住等不能移动的安排；
- 预算、交通、住宿、行李、餐食、无障碍和活动偏好；
- 不能妥协的条件、优先顺序以及可接受的价格或时间交换关系。

模型可以提出语义解释，程序负责校验人员引用、日期、单位和值域。缺少的信息会改变行程是否成立时，系统不能静默猜测。

### PR-02 来源查询与并行探索

- 根据旅行结构生成日期、行程段、组件和来源任务；
- 日期与平台使用固定工作池并行，不为每个任务复制 Agent；
- 相同查询只执行一次，候选、默认方案和个性化方案共享结果；
- 每个来源明确记录成功、无结果、验证码/登录阻断、页面失败或信息不足；
- 每个本次已授权且能力匹配的平台都必须被查询或得到明确状态，不能只挑成功平台进入报告；
- 全部合法日期必须进入查询计划；可以用价格下界等可证明方法提前排除，但不能静默只查 Top N；
- 结果展示本次覆盖范围，不把失败平台算作已比较成功。

### PR-03 报价与整趟费用

每个报价必须说明：

- 来源、查询时间、产品身份和可继续查看的入口；
- 适用日期、同行者、房间或容量；
- 按每人、每房晚、每段、整团、往返票还是整包计价；
- 币种、税费、服务费和仍未知的费用；
- 与其他报价是否为同一产品和是否可以公平比较。

共享房价、往返票、联程票和酒店含接驳只计算一次。最终卡展示整趟人民币总费用和各组件费用；关键费用不完整时不能发布最终方案。

同一具体产品的直接价差比较必须使用稳定产品身份：航班至少对齐每一段的日期、航班号、舱等/行李和适用人数；酒店至少对齐酒店、房型、入住退房、餐食、取消条件和入住人数。不同产品不能标成“同款价差”，但各自满足要求后可以与其他来源组件交叉组合，再比较整趟总费用，例如平台 A 的航班加平台 B 的酒店。

### PR-04 行程组合与选择

- 每位同行者的时间和地点必须连续且没有冲突；
- 住宿覆盖每个需要过夜的日期，并满足房间与人数；
- 固定活动前后有足够交通与缓冲；
- 当前单目的地固定结构继续使用现有快速组合；
- 多城市、房间、活动和人员分合流使用适合有限候选的确定性求解器；
- 先排除不能成行的方案，再形成价格、时间、舒适度、位置和便利性的 Pareto 候选；
- 求解结果明确区分无解、找到可行解和在本次候选范围内已证明最优。

### PR-05 偏好与代表方案

- 当前请求中的偏好优先于所有历史记录；
- 用户偏好明确时返回一份最终建议；
- 偏好不足时返回省钱、均衡和体验优先三份不重复的代表方案；
- 用户确认的稳定偏好和有条件偏好可以跨旅行使用；
- 历史选择只能作为弱参考，不能自动升级为长期规则；
- 价格、库存、班次和页面内容永不写入长期记忆；
- 用户能够查看和撤销长期偏好。

### PR-06 三角色 Multi-Agent 个性化面板

同一份候选目录存在多个有意义的非支配方案时，固定启动三个真实 Agent：价格 Agent、体验 Agent 和综合决策 Agent。前两个 Agent 并行提出不同角度的候选提案，综合决策 Agent 通过 typed handoff 接收两份提案，再结合当前用户偏好提出最终候选。亲子、长辈、无障碍等额外 Skill 或专业角色只在对应场景加入，不按日期或平台数量复制团队。

每个 Agent 只看到相关旅行子图、有限候选、程序检查、适用偏好、允许工具和相关 Skill。Agent 只能提交绑定 `graph_version` 和 `source_refs` 的候选提名，不能直接修改价格、旅行图或最终方案；程序负责验证和仲裁。候选唯一时可以走确定性快路径，这只是没有语义取舍时的性能优化，不是产品的无模型对照组。

### PR-07 自然语言修改与变化重规划

- 用户可以修改酒店、交通、日期、同行者、活动或偏好；
- 系统识别受影响的组件、人员、日期和来源；
- 用户要求保留以及未受影响的组件继续锁定；
- 只补查受影响范围，然后重新求解并完整复算整趟行程；
- 局部无解时逐步扩大调整范围，不能静默改掉用户要求保留的内容；
- 修改失败时保留原方案；
- 新旧方案显示组件、时间、人数和费用差异。

### PR-08 完整行程任务接口

原生界面、API、MCP 和其他 Agent 宿主共享同一个旅行任务与最终方案。对外提供：

1. 创建旅行规划；
2. 查询任务进度；
3. 读取当前结果；
4. 用自然语言修改方案。

外部宿主不需要知道 TripChord 内部有哪些 Agent，也不能绕过 TripChord 的组合、复算和最终检查。

## 6. 最终行程卡

每一份最终方案使用同一种中文卡片，至少包含：

| 区域 | 必须展示的内容 |
| --- | --- |
| 行程概览 | 出发与返程当地日期、旅行天数、目的地顺序、同行者 |
| 每日安排 | 日期、当地时间、地点、交通、住宿、固定活动和必要缓冲 |
| 交通 | 起终点、班次/车次、当地日期时间、时长、行李或关键条款；名称链接到对应来源 |
| 住宿 | 酒店、房型、入住退房、适用人员、早餐与取消信息；名称链接到对应来源 |
| 接驳与活动 | 集合地点、时间、时长、适用人员和关键限制；可查询活动的名称链接到对应来源；用户已持有或自行提供的固定安排明确标为用户输入，可没有购买链接 |
| 费用 | 各组件人民币费用、共享费用覆盖范围、每位同行者相关费用和整趟总费用 |
| 选择理由 | 与其他可行候选相比，为什么更符合本次偏好 |
| 查询范围 | 本次查询的日期、来源、成功与失败状态、查询时间 |
| 待确认项 | 预订前仍需在来源页面核对的内容；存在关键缺口时只能显示候选，不能标为最终方案 |
| 修改差异 | 修改前后哪些内容保持、替换、增加或减少，以及总费用变化 |

## 7. 七次迭代总览

| 次数 | 用户得到的新能力 | 主要架构切片 |
| --- | --- | --- |
| **1** | 当前单目的地需求能快速完成真实跨来源整趟比价，得到满足要求后的最低总价完整行程卡 | 最小通用旅行合同、PriceContract、PlanGraph、旧求解器适配、全窗口查询计划 |
| **2** | 在一个范围受控的当前来源场景中完成多城市、异地进出和固定时间活动规划 | RequirementGraph、原子交通段、TripAnchor、第一版复杂场景求解 |
| **3** | 在一个范围受控的当前来源场景中完成分地出发、汇合、分开活动和提前返程规划 | Traveler/TravelerGroup、人员作用域、共享价格与逐人连续性 |
| **4** | 偏好明确时给一个答案；偏好不足时给三种答案；复杂候选由价格、体验、综合决策三个 Agent 协作，并记住已确认偏好 | Pareto、偏好编译、三角色面板、上下文投影、旅行 Skill、条件记忆 |
| **5** | 能对复杂方案进行自然语言修改，并在价格或班次变化后尽量只调整受影响部分 | TripRun、PlanVersion、依赖传播、局部补查与重新求解 |
| **6** | 实时方案能够加入至少一种新交通方式和可在线查询的活动 | 新 Offer 类型、来源连接、相关 Skill、同一组合与行程卡 |
| **7** | 其他 Agent 或聊天应用可以创建、等待、读取和修改完整 TripChord 任务 | 四个粗粒度 API/MCP 能力、统一任务状态、2.0 交付矩阵 |

### 为什么当前拆成七次

七次是当前实施切分，不是不可改变的数学结论。它遵守四条依赖：先补齐当前真实比价；把路线拓扑和人员分组分开验证；把 Agent、记忆和 Skill 与它们真正服务的个性化选择放在同一轮；把只能放大现有能力的 MCP 放在最后。若端到端结果证明两轮可以安全合并或必须拆开，以真实结果更新本文，而不是为了维持数字继续执行。

## 8. 每次迭代的详细范围

### 迭代 1：可信且快速的单目的地完整方案

**用户结果**

用户提交当前杭州至马尔代夫这类灵活日期需求后，TripChord 不再只给 Top 3 中的当前候选，而是完成已声明范围内的跨来源比较，输出返程、酒店、接驳、同行人数、人民币总费用和来源链接都完整的一张行程卡。本轮在满足明确要求后选择整趟总费用更低的方案，不提前声称已经实现个性化最优。

**本轮完成事项**

- 增加当前场景需要的最小 `TravelIntent`、`Traveler`、`PlaceRef`、`PriceContract` 和 `PlanGraph`；
- 当前 `PackagePlanner` 通过适配器成为第一个 `PlanSolver`，不重写真实查询链；
- 本次已授权且能力匹配的所有已连接平台都必须得到成功、无结果或失败状态；不能遗漏后再声称完成平台比较；
- 至少两个平台对同一具体产品或满足同一需求的可替代产品返回日期、人数和费用口径完整的报价；同款价差与不同产品的整趟方案比较分别展示；
- 允许平台 A 的航班、平台 B 的酒店和其他来源的接驳交叉组合；每种有效组合都按整趟人民币总费用比较，而不是只比较酒店或机票页面价；
- 全部合法日期进入查询计划，每组都有详查、被可证明地排除或来源失败状态；
- 通过固定工作池、相同查询复用和候选剪枝缩短等待，但不静默抽样；
- 统一输出最终行程卡，并明确本次来源与日期覆盖。

**端到端完成标准**

1. 保存来源基线通过新合同后，选中组件、整趟总费用、来源引用和修改结果与当前路径一致；
2. 从正式中文入口运行参考需求，所有已授权且能力匹配的平台都有明确状态，至少两个平台形成可比较报价并进入跨来源完整行程组合；
3. 所有合法日期都有可审计状态，没有只详查 Top 3 后声称完成全窗口；
4. 选中方案的航班、住宿、接驳、税费、人数和返程全部闭合，输出可决策的中文卡；
5. 在登录状态正常、来源未触发验证码或限流的固定参考环境中，从创建任务到最终卡的启动目标不超过 **10 分钟**。参考清单固定日期窗口形态、旅行天数、同行者、启用来源与机器环境，并分别记录 TripChord 内部处理和平台等待；同时保存改造前同环境基线。十分钟是待迭代 1 校准的产品假设，不是当前事实，若真实平台访问节奏证明它不合理，必须基于数据修订而不能静默放宽。

**本轮不包含**

多城市、分地出发、活动报价、完整 CP-SAT、MCP 或新增 Agent 团队。

### 迭代 2：多城市、异地进出与固定活动

**用户结果**

用户可以说“杭州到大阪，再去京都，东京返程；周六晚必须在大阪参加演唱会”，并在一个日期和来源范围受控的当前查询中得到时间地点连续的完整行程卡。本轮仍沿用“满足明确要求后整趟总费用更低”的选择规则，不声称已经完成个性化取舍。

**本轮完成事项**

- 完整 `TravelIntent`、多个 `PlaceRef`、`TripWindow` 和 `TripAnchor`；
- 本轮固定活动是用户已提供或已持有的 `TripAnchor`，不是实时活动报价：用户给出已支付费用时，以“用户提供费用”单独计入；未给费用时明确标成未计入整趟总费用，不能猜测价格，也不要求购买链接；
- RequirementGraph、OfferGraph 和 PlanGraph 进入同一正式入口；
- 往返报价能够表达为原子交通段与共享价格合同；不可拆整包继续保留为 BundleOffer；
- 多段交通、各城市住宿夜晚、固定活动和必要缓冲统一求解；
- 当前单目的地求解器继续作为快速路径；复杂有限候选使用第一版 CP-SAT 参考求解；
- 行程卡展示城市顺序、各段交通、住宿、固定活动和整趟总费用。

**端到端完成标准**

1. 一个冻结的多城市来源集从正式自然语言入口输出完整卡，并与小规模可枚举答案核对；
2. 一个日期范围受控的当前来源场景从查询多段交通和住宿开始，最终输出完整卡；不能只证明各段能查询，也不能混入手工价格；
3. 固定活动前后时间、地点和缓冲成立，住宿覆盖全部夜晚；
4. 新场景复用同一个需求、报价、求解、复算和行程卡流程，没有大阪、东京等城市专用分支；
5. 迭代 1 的单目的地正式入口、组件、总费用和覆盖结果继续通过；迭代 2 的完整规划参考场景满足第 9 节统一的十分钟启动目标，实际差值及平台等待单独报告。

**本轮不包含**

分地出发、部分人员参加活动、长期偏好学习或新交通来源。

### 迭代 3：多人分地出发、汇合与分流

**用户结果**

两组人可以从不同城市出发，在目的地汇合；部分人参加某个活动或提前返程。TripChord 在一个范围受控的当前来源场景中同时给出共同安排、每个人的路线和整团总费用。本轮仍不声称所有人数与目的地都已得到实时覆盖。

**本轮完成事项**

- 每位 `Traveler` 具有独立出发地、时间范围和旅行要求；
- 使用明确的 `TravelerGroup` 表达一起行动或共享报价的人群；
- 每个交通、住宿、接驳和活动组件带参与人员范围；
- 房间容量、共享房价、团体报价和往返套票通过 PriceContract 只计算一次；
- 求解器检查每个人的时间地点连续性、汇合与分流；
- 行程卡同时提供整团视图和按人查看的安排与费用。

**端到端完成标准**

1. “杭州和北京分别出发、大阪汇合、部分人不参加活动、其中一人提前返程”从正式入口得到完整卡；
2. 每个人全程没有时间重叠或地点断裂；
3. 共享酒店、活动和套票不重复计价，个人费用与整团总费用能够对账；
4. 新场景不复制一套“多人规划流程”，现有单人和单出发地仍走相同中央合同；
5. 一个范围受控的当前来源运行从两个出发地查询到最终卡，验证不同出发地报价、共享住宿和各自返程确实进入同一完整方案。

**本轮不包含**

任意人数规模优化、企业团建审批、费用分摊结算或代付款。

### 迭代 4：个性化方案与三角色 Multi-Agent 面板

**用户结果**

用户说清偏好时得到一份真正按其取舍选择的方案；偏好不足时得到省钱、均衡和体验优先三种方案。复杂候选由价格、体验和综合决策三个 Agent 共同完成取舍，带父母、儿童或特殊需求时再加入相关专业 Skill 或角色。

**本轮完成事项**

- 从已证明可行的方案中形成价格、时间、舒适度、位置和便利性的 Pareto 集合；
- 可计算维度由程序生成，住宿与活动体验判断必须绑定来源；
- 当前偏好编译成优先顺序或明确交换关系，不使用所有人共用的永久权重；
- 实现固定三角色面板：价格与体验并行，综合决策接收 typed handoff；
- 需求歧义、来源冲突、体验取舍和特殊风险作为面板输入或额外 Skill 的触发条件；
- Agent 只看到相关子图、候选、程序检查、适用偏好、工具和 Skill；
- 保存用户确认的稳定或有条件偏好，当前请求仍能覆盖；
- 三种代表方案复用同一次查询，选择后收敛成一份最终卡。

**端到端完成标准**

1. 同一批来源分别运行价格优先、舒适优先和偏好不足三种输入，推荐会按取舍真实变化；
2. 三种代表方案成立、不重复，且没有重新访问三遍来源；
3. 简单且结果唯一的任务跳过决策与风险模型，最终方案不变；
4. 使用同一来源快照完成价格/体验并行提案、综合决策接收两份 `peer_proposals`、三条 trace 均通过校验，并由程序在提名集合内仲裁出最终候选；
5. 记录绝对的最终可行率、偏好符合度、无来源事实错误、模型调用、token 与等待时间；不把无模型比较设为 Multi-Agent 面板的通过门槛，也不据此外推它在所有任务上优于单 Agent；
6. 没有新增语义冲突时，单纯增加日期或来源任务不会触发更多角色类型；固定基准中的模型调用不随普通查询任务线性增长。新增来源确实带来独立冲突时允许调用相应角色，但必须记录原因；
7. 每次调用保存 Context Manifest：只包含相关子图、有限候选、程序检查、适用偏好、工具与 Skill 版本；至少一个场景证明相关 Skill 改变了可核对的判断；
8. Agent 提议绑定 `graph_version` 和来源引用；旅行状态更新后，旧版本提议必须被拒绝，不能进入最终卡；
9. 用户确认的“带父母时少换乘”等条件能影响下一次适用旅行，旧价格和班次不会进入记忆。

**本轮不包含**

按日期或平台复制完整团队、Debate、投票、BFT 共识、新 Agent Runtime 或大量没有触发场景的 Skill；复杂候选的三角色面板属于本轮主路径。

### 迭代 5：复杂方案修改与变化重规划

**用户结果**

用户可以对多城市或多人方案说“保留演唱会和航班，只把酒店换到车站附近”；当用户或来源连接提交酒店售罄、价格变化或班次变化事件后，也能得到尽量少改动的新方案和清晰差异。本轮消费变化事件，不承诺持续自动监控平台。

**本轮完成事项**

- `TripRun` 成为所有入口共用的唯一旅行状态；
- 每次修改生成新的 `PlanVersion`，保留上一版和差异；
- 依赖边覆盖时间、地点、同行者、住宿、固定活动和共享价格合同；
- 自然语言修改映射到组件、人员、条件或偏好；
- 接收用户或来源连接提交的结构化变化事件，按事件类型传播影响，锁定未受影响组件，只补查相关日期、地点、人员和来源；
- 局部无解时逐级扩大范围，最后才完整重算；
- 新方案重新核对整趟费用、时间地点和每位同行者，而不是只检查修改部分；
- 行程卡展示保持、替换和费用变化。

**端到端完成标准**

1. 酒店修改只替换酒店和必要接驳，要求保留的航班与固定活动逐项不变；
2. 一名同行者退出后，其专属组件移除，共享组件和整团费用正确重算；
3. 用户或来源连接提交一个变化事件后，只重新查询受影响范围，但最终对整趟方案进行复算；本项不冒充自动发现变化；
4. 局部修改无解时原方案继续保留，系统解释需要扩大哪些调整；
5. 不出现运行框架、MCP、浏览器任务和规划器各自保存一份最终答案的情况；
6. 对“只换酒店”这类受影响范围明显小于整趟旅行的参考修改，外部查询数必须严格少于完整重算，端到端耗时的启动目标不超过同环境完整重算的 **50%**；若真实来源固定等待使比例失真，必须分别报告内部处理和平台等待并重新校准，不能以“已局部查询”代替速度改善。

**本轮不包含**

自动改签、取消预订、锁定库存或支付差价。

### 迭代 6：新交通方式与可查询活动

**用户结果**

完整行程不再只包含机票、酒店和接驳，而是能够加入至少一种新的交通方式以及一个可在线查询的活动，并统一比较整趟费用与体验。

**本轮完成事项**

- 接入至少一种非航空交通，例如铁路或轮渡；
- 接入至少一种具有时间、适用人员、当前价格和查看入口的活动；
- 新来源返回相同的 OfferEnvelope、PriceContract 和来源状态；
- 新组件进入同一时间地点连续性、整趟总费用、Pareto 选择和行程卡；
- 只增加组件类型、来源连接或相关 Skill，不修改中央工作流；
- 根据真实来源特点补充必要的业务检查，而不是先建设通用平台框架。

**端到端完成标准**

1. 一个日期与目的地范围受控的真实需求，从正式入口查询新交通和活动来源；
2. 最终卡同时包含交通、住宿、活动、接驳、整趟人民币总费用和来源入口；
3. 来源时间、覆盖范围、失败项和费用口径被封存，保存数据只用于复现，不冒充当前价格；
4. 删除新组件后中央规划流程不需要分叉；再次增加同类型来源只需新增连接模块；
5. 这次真实运行保持在小范围内，目标是证明扩展机制，不重复一次耗时数天的全窗口实验。

**本轮不包含**

一次接入所有交通方式、所有活动平台或宣称广泛目的地覆盖。

### 迭代 7：外部 Agent 接入与 TripChord 2.0

**当前证据状态（2026-08-26）**：已用 Claude Code 2.1.245 作为真实宿主、官方 Python MCP SDK 1.29.1 作为独立客户端完成范围受控当前来源验证；证据见 [`benchmarks/results/i7-mcp-current-2026-08-26.json`](../benchmarks/results/i7-mcp-current-2026-08-26.json)。本条证明 I7 已完成其声明范围，不扩展为所有宿主覆盖。

**用户结果**

用户能够从其他聊天助手、桌面应用或 Agent Harness 创建 TripChord 任务，断开后继续查询进度、读取同一行程，并用自然语言修改它。

**本轮完成事项**

- 提供 `create_plan`、`get_plan_status`、`get_plan`、`modify_plan` 四个粗粒度 API/MCP 能力；
- 外部入口和原生界面使用同一个任务 ID、TripRun、来源快照和 PlanVersion；
- 外部宿主只负责对话与展示，不调度内部 Agent，也不重新计算价格；
- 任务进度使用用户能理解的旅行结果节点；
- 外部修改继续经过影响分析、重新求解、整趟复算和最终行程卡；
- 汇总 2.0 的真实运行、冻结场景、Agent 对照、耗时和已知边界；
- 七轮矩阵通过后，版本与公开项目声明统一更新为 2.0.0；仍必须保留当前来源与冻结来源的证据边界。

**端到端完成标准**

1. 在实现前选定一个真实目标宿主，例如 Oh My Pi、DeepSeek Harness 或当时可用的同类 Agent；由该宿主创建复杂旅行任务，断开后按任务 ID 取回同一结果；内部自制脚本不能单独通过本项；
2. 同一能力额外通过一个标准 MCP 客户端，证明接口不只绑定选定宿主；
3. 真实宿主提交“保留航班，只换酒店”，得到新 PlanVersion 与差异卡；
4. 原生界面、真实宿主和标准 MCP 客户端读取到相同状态与最终方案；外部入口不得创建第二个规划任务或重复查询来源；
5. 外部宿主不需要知道内部 Agent 名称，也不能绕过最终核对；
6. 对同一任务比较原生入口和外部宿主，规划阶段必须复用同一 `TripRun`，不得产生第二次规划或重复查询；协议与展示的耗时增量记录为报告项，不用“明显”一类主观词作为完成门槛；
7. 2.0 验收矩阵覆盖单目的地、多城市、分组同行、个性化、变化重规划、新组件和外部接入；
8. 发布说明准确区分冻结数据、范围受控的真实查询、当前可用能力和仍未覆盖的来源。

**本轮完成后的准确定位**

TripChord 2.0 的准确含义是：正式入口已经验证当前单目的地场景、一个范围受控的多城市异地进出场景、一个范围受控的分地出发与分流场景，以及一个新交通和活动场景；复杂候选三角色 Multi-Agent 面板、确认偏好记忆、自然语言修改和真实宿主调用也已分别在 2.0 验收矩阵中通过，其中至少一个复杂方案完成了外部宿主读取与修改。它不表示每种旅行结构与所有能力的任意组合都已验证。每项结果必须继续标明使用的是冻结来源还是当前来源；它也不代表已经泛化到任意复杂自由行、生产级商业服务、全平台最低价、所有目的地覆盖或自动预订。

## 9. 每轮共同完成标准

每次迭代只有同时满足以下条件才算完成：

1. 从正式自然语言入口开始，不从内部对象或手工脚本中途起跑；
2. 经过真实产品使用的查询、归一、求解、选择、复算和行程卡路径；
3. 该轮新增能力至少有一条端到端场景；涉及来源能力时，必须有范围受控的当前来源运行；
4. 冻结来源可以验证算法和快速回归，但不能代替本轮需要证明的实时能力；
5. 前面迭代已经成立的用户结果继续通过，不靠创建第二套入口或第二套状态完成；
6. 记录准确输入、来源范围、最终状态、耗时、实际调用角色和最终卡；
7. 用户不能妥协的条件、每位同行者连续性和整趟费用全部由程序复查；
8. 代码量、测试数、覆盖率、Agent 数、Skill 数和文档数量不计入产品进度；
9. 测试优先使用正式入口端到端流程，冻结基准用于定位和回归，单元测试不能代替最终复验；
10. README、简历、面试稿和架构文档只能随真实能力更新，不能单独成为一轮迭代；
11. 迭代 1、2、3、4、6 各自固定一个范围受控的完整规划参考场景，在正常来源条件下沿用“任务创建到最终卡不超过 10 分钟”的启动目标，并分别记录需求理解、平台等待、归一、求解、模型判断和输出耗时。该目标在迭代 1 用改造前后基线校准；后续若真实数据证明需要调整，必须更新 PRD 与理由，不能让复杂场景重新变成数小时任务仍宣布完成。

## 10. 2.0 完成定义

七次迭代已按 [2.0 公共验收矩阵](v2.0-acceptance.md) 完成范围受控验收，因此可以称 **TripChord 2.0 功能形态完成**，因为：

- 当前单目的地真实核心不退化，并完成声明范围内的跨来源整趟比价；
- 多城市、异地进出、分地出发、人员合流与分流使用同一领域内核；
- 用户偏好能真实改变选择，无偏好时有三种代表答案；
- 复杂候选固定运行价格/体验/综合决策三角色面板；额外专业角色按场景加入，日期和平台不复制团队；
- 复杂修改和来源变化能够生成尽量少改动的新方案；
- 至少一个新交通类型和一个可查询活动进入真实完整行程；
- 外部 Agent 能够调用完整 TripChord，而不是拼装内部角色；
- 每项声明都有对应的正式入口端到端结果。

这仍只说明**产品功能与目标架构在声明范围内闭合**。只有真实用户持续使用并认可建议、当前来源成功率与等待时间达到预期，才能进一步称价值已经实现或产品已经成熟。

## 11. 非目标与停止条件

### 2.0 之前不单独排期

- LangGraph、CrewAI、AutoGen 等 Runtime 迁移；
- 图数据库、分布式基础设施或通用工作流平台；
- 按日期或平台复制完整 Multi-Agent 团队、Debate、投票或 BFT 共识；保留复杂候选上的三角色取舍面板；
- 手机原生应用、签名安装包或大规模无头浏览器集群；
- 为平台数量、Agent 数量、Skill 数量或测试覆盖率设里程碑；
- 与真实主线无关的安全扩张、数据库重构和低概率边界建设；
- 付款、下单、锁定库存、改签、取消或预订管理。

### 必须停止当前做法并重新检查架构

- 新旅行结构需要复制中央工作流或加入城市专用分支；
- 报价无法准确说明覆盖的人员、日期与组件，导致总费用不能闭合；
- 同一局部错误连续两次修复仍无法通过同一端到端流程；
- 新合同不能等价承接当前单目的地结果；
- CP-SAT 成为平台查询之外的新主要瓶颈，且专用求解器在同一数据上明显更好；
- 三角色提案没有形成可解释取舍，或综合角色的 handoff 没有进入最终选择；此时重审角色边界、并行策略和模型路由，而不是退回无模型对照作为主路径；
- 连续两轮只有内部交付物增加，没有新的用户结果。

出现这些事实时，先说明真实现象、已尝试内容和受影响范围；只有证据表明机制或架构不合理时才调整主架构，不能因为普通实现问题重新开启框架选型。
