# TripChord 产品形态与实施路线

> 本文面向开发者和面试讨论，说明 TripChord 最终要做成什么，以及从当前版本到这个形态的实施顺序。当前已经交付的能力以 [1.0 桌面核心验收](v1.0-acceptance.md) 为准；本文中的后续目标不能当作现有功能介绍。

## 当前结论

截至 2026 年 8 月 23 日，**产品边界和核心架构已经确定，可以直接进入实施**。下一步不再继续比较 Agent 框架，也不再增加第二个耗时很长的旅行需求；沿用杭州至马尔代夫的真实需求，把当前最重要的缺口逐个打通。

当前 1.0 已经把自然语言需求、合法日期生成、只读平台查询、报价整理、交通住宿接驳组合、人民币费用、长期偏好保存和自然语言修改接到同一条桌面主链上。仍未完成的是：多个平台在同一次查询中稳定返回可公平比较的报价、个人偏好真正改变最终选择、无偏好时给出三种代表方案，以及完整灵活日期窗口的快速查询。

## 完整产品形态

用户可以直接说：

> 8 月 20 日到 9 月 10 日之间，从杭州去马尔代夫玩 4–7 天，3 位成人和 1 名 7 岁儿童，两间房。不要住得偏，尽量少中转，希望整体划算。

TripChord 在后台完成日期展开、多个平台查询、报价核对、完整行程组合和费用计算，并根据用户表达方式给出答案：

- 用户已经说清更在意什么时，只给一份最符合本次取舍的方案；
- 用户没有表达足够偏好时，给出省钱、均衡和体验优先三种代表方案；
- 每份方案都有去程、返程、住宿、接驳、所有人的人民币总费用、选择理由和仍需在预订前确认的内容；
- 用户可以说“换酒店但保留航班”或“再便宜一点”，系统只重查受影响的部分，再重新检查整趟行程；
- 用户确认过的稳定偏好可以长期保存；价格、库存和班次每次重新查询；
- TripChord 只查询、比较和建议，不下单、付款或修改预订。

## 已经确定的架构

| 问题 | 已确定的选择 |
| --- | --- |
| 产品核心 | TripChord 是可以独立使用的旅行规划 Agent，自己负责从需求到最终方案的完整过程。 |
| 真实数据 | 平台连接模块只负责取得当前结果；TripChord 统一具体产品、日期、人数、税费和币种后再比较。 |
| 模型职责 | 模型理解语言、体验和难以写成固定公式的取舍；不能决定日期是否合法、金额是多少或行程是否成立。 |
| 组合算法 | 先排除不可行方案，再构造交通、住宿和接驳的离散组合，使用 Pareto 集合处理价格、时间与体验的多目标选择。 |
| 灵活日期 | 程序生成全部合法日期；日期组合是并行工作项，不为每个日期复制一组 Agent。 |
| Multi-Agent | 角色按实际问题触发；确定性结果已经足够时跳过模型，只有语义取舍、风险或修改需要时才调用相应角色。 |
| 偏好与记忆 | 当前请求优先于历史偏好；长期只保存用户确认过的稳定偏好，实时价格和库存不能进入记忆。 |
| 运行框架 | 生产主链保持当前实现。PydanticAI 只作为以后可能替换模型调用层的候选；LangGraph 等框架不进入本轮实施。 |
| 对外接入 | 以后通过完整任务接口或 MCP 提供“创建规划、查询进度、修改行程”，外部应用不控制 TripChord 内部角色。 |

完整理由、备选方案和重新评估条件见 [重要架构决策](architecture-decisions.md)。

## 实施顺序

### 第一阶段：在同一次查询中真正完成跨平台完整行程比价

**用户得到的结果**

同一日期、相同出行人数和住宿要求下，至少两个已连接平台返回可以直接比较的当前住宿报价。TripChord 将它们分别与航班和接驳组合，重新计算整趟旅行的总费用，再选择更优的完整行程，并说明本次实际比较了哪些平台。

**实施重点**

- 沿用现有杭州至马尔代夫需求，先固定其中一个已知可行日期；
- 修复去哪儿住宿或另一个已接入来源无法稳定产出准确报价的真实原因；
- 不使用手工补价、保存回放或“页面能打开”代替当前报价；
- 交通、住宿和接驳继续沿用统一的日期、人数、产品和费用合同。

**端到端完成标准**

从正式产品入口发起一次只读查询；至少两个住宿平台在相同日期、人数和住宿要求下返回准确报价；各自进入完整行程并重新计算航班、住宿与接驳总费用，最终方案采用其中整趟费用更优的一份。结果页同时显示另一候选、查询时间与覆盖范围；若两个平台提供的是同一家酒店和同一房型，再额外展示同产品价差。

### 第二阶段：让个人偏好真正决定答案

**用户得到的结果**

同一批真实候选可以根据不同用户的取舍产生不同答案，而不是永远选择最便宜的一份。没有偏好时，系统一次给出省钱、均衡和体验优先三种代表方案。

**实施重点**

- 保留不可妥协要求的程序过滤；
- 在剩余候选上构造价格、总耗时、中转、住宿品质、位置和便利性的 Pareto 集合；
- 价格和时间来自可计算事实，住宿品质和位置判断必须绑定来源信息；
- 当前请求覆盖长期偏好；不使用一个对所有用户永久固定的权重公式；
- 三种答案复用同一次查询和同一批候选，不重复访问平台。

**端到端完成标准**

使用同一份真实候选数据运行三次：省钱偏好、舒适偏好和无偏好。前两次各返回一份符合相应取舍的方案；无偏好时返回三种不重复、理由可核对的代表方案。任何没有来源支持的体验维度都不能参与选择。

### 第三阶段：把完整灵活日期查询压缩到可接受时间

**用户得到的结果**

像“21 天内出去玩 4–8 天”这样的需求，不再因为日期组合多而等待数小时或数天；系统明确完成了多少合法日期，并在一次运行中复用所有能够复用的查询。

**实施重点**

- 全部合法日期由程序一次生成；
- 日期组合使用固定工作池，平台分别设置并发和访问节奏；
- 航班、住宿和接驳可以并行，完全相同的查询通过稳定指纹共享一次结果；
- 同一批候选同时服务省钱、均衡、体验和个性化选择，不为每种答案重新搜索；
- 先用保存来源数据验证调度计划，再只做一次完整真实平台运行。

**端到端完成标准**

杭州至马尔代夫参考需求生成的全部 85 组合法日期都进入同一次任务并得到明确结果，没有静默抽样；调度与去重先用保存来源数据证明满足十分钟预算，随后一次真实只读全窗口运行也必须在十分钟内完成。若超时，这一阶段仍未通过，应记录主要耗时来源并继续修复，不能把“已经解释超时”当作完成。

### 第四阶段：让 Multi-Agent 只在有价值时参与

**用户得到的结果**

简单需求更快，复杂偏好仍能得到专业判断；用户不会为每个日期、每个平台或每个固定检查承担重复的模型等待。

**实施重点**

- 程序已经得出唯一结果时，跳过方案选择模型；
- 只有出现真实的价格与体验取舍时才调用方案选择角色；
- 只有存在中转、入住、位置等不确定风险时才调用风险角色；
- 只有发生修改或外部变化时才调用相应诊断和调整角色；
- 日期和平台查询始终是普通并行任务，不包装成 Agent。

**端到端完成标准**

用同一组旅行输入对比固定调用全部角色与按需调用：最终方案质量不下降，模型调用和等待时间明显减少；每个实际调用的角色都能说明它改变了什么判断，未调用角色不会被写成已经参与。

### 第五阶段：让其他 AI 应用调用完整的 TripChord

**用户得到的结果**

用户可以从聊天助手、桌面工具或自动化环境发起 TripChord 规划，不必了解内部模型角色，也不会因为更换入口而重复查询。

**实施重点**

- 提供创建规划、查询进度和修改行程三个粗粒度接口；
- 优先采用 MCP 作为通用 Agent 工具入口，同时保留现有 API 和原生界面；
- 所有入口共享同一个任务身份、偏好规则、候选和最终方案；
- Oh My Pi、DeepSeek Harness 或其他宿主只负责交互与展示，不接管价格计算和方案选择。

**端到端完成标准**

外部客户端可以创建一个任务、断开后按任务 ID 取回结果，再提交“换酒店但保留航班”的修改；整个过程复用原任务，未受影响的组件不重复搜索。

## 当前不进入实施的内容

- 不迁移到 LangGraph、CrewAI、AutoGen 或其他新运行框架；
- 不增加第二个多日真实旅行需求；
- 本轮不建设与真实主线无关的通用基础设施，也暂不做移动端、安装器或更多目的地；
- 不用单元测试数量、Agent 数量、平台数量或框架数量代替端到端结果；
- 不做自动下单、付款、接受条款、锁定库存或修改预订。

这些事项只有在上面的主链完成后，或真实端到端运行证明它们已经成为主线阻碍时，才重新排期。

## 什么时候重新讨论架构

只有出现下面的真实事实，才重新开启架构选型：

- 实际候选规模使现有组合器无法在时间预算内完成；
- 当前运行方式直接阻碍平台并行、任务继续或按需模型调用，而且局部替换无法解决；
- 用户偏好无法在现有旅行合同中表达；
- 某个候选框架通过同一端到端任务证明能改善最终方案、等待时间或维护成本，并且不会产生第二套旅行状态。

在此之前，下一步就是执行第一阶段，而不是继续研究框架。
