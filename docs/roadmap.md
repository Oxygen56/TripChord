# TripChord 产品形态与实施路线

> 本文说明 TripChord 最终要做成什么，以及从当前 1.0 走向完整形态的实施顺序。已经交付的能力以 [1.0 验收记录](v1.0-acceptance.md) 为准；后续目标不能当作现有功能介绍。

## 当前结论

TripChord 的长期定位是面向个人或多人复杂自由行的旅行决策 Agent。当前 1.0 已经跑通“单出发地、单目的地往返”的首个纵向切片：自然语言需求、灵活日期、只读来源查询、机票住宿接驳组合、人民币总费用、偏好记忆和自然语言修改进入同一条主链。

下一步不再把马尔代夫专用套餐继续扩展成万能对象，也不推倒真实链重写。主路线是增加统一旅行合同和领域图，让当前链成为第一个专用求解器，再用结构差异明显但快速可重复的场景证明架构。完整设计见[复杂自由行目标架构](target-architecture.md)。

## 完整产品形态

未来用户可以这样描述旅行：

> 9 月从杭州和北京分别出发，在大阪汇合后一起去京都。周六晚必须到大阪参加演唱会，老人尽量少换乘，孩子只参加前半程。返程可以从东京走，预算适中，优先住交通方便的酒店。

TripChord 应完成：

- 理解每位同行者的出发地、可出行时间、共同与单独活动；
- 展开可行日期、城市顺序和交通方式；
- 并行查询当前可用的交通、住宿、接驳和活动；
- 统一每个报价覆盖的人员、日期、组件、税费和币种；
- 组合出每个人时间地点连续、整团总费用准确的完整行程；
- 用户说清偏好时只给一份最合适方案；偏好不足时给出省钱、均衡和体验优先三个代表方案；
- 用户修改或来源变化后，只重新查询和求解受影响部分；
- 记住用户确认过的稳定偏好，但每次重新查询价格、库存和班次；
- 输出一张中文行程卡，并提供对应平台或官网入口；
- 永远只查询、比较和建议，不替用户交易。

## 已确定的架构

| 问题 | 决定 |
| --- | --- |
| 产品内核 | TripChord 自己掌握旅行需求、来源结果、组合求解和最终方案；外部 Agent 只能调用完整能力 |
| 旅行表达 | 类型化 `TravelIntent` + RequirementGraph、OfferGraph、PlanGraph 三种领域视图 |
| 价格 | 用 `PriceContract` 表达每人、每房晚、整团、往返票和整包，避免重复计费 |
| 求解 | 当前固定结构走现有快路径；复杂有限候选优先 CP-SAT；RCSP 只在同数据基准证明收益后加入 |
| 多目标 | 先证明可行，再保留 Pareto 候选；用户取舍采用优先顺序或明确交换关系，不使用永久统一权重 |
| Multi-Agent | 确定性 Need Router 按歧义、冲突、取舍和特殊风险触发；日期、来源和候选只是普通并行任务 |
| 上下文 | Agent 只看到相关子图、有限候选、程序检查、适用偏好和允许工具，输出带版本的提议 |
| 记忆 | 当前请求优先；长期只保存用户确认的稳定或有条件偏好；实时旅行事实只属于本次运行 |
| Skill | 保存亲子、长辈、中转、自驾等可版本化旅行方法，不保存价格，也不能绕过程序核对 |
| Agent Runtime | 继续使用现有实现；领域内核与 Runtime 解耦，不为了框架标签迁移 |
| 对外接入 | API/MCP 只提供创建规划、查询进度、修改和读取结果，不暴露内部角色 |

## 实施顺序

### 一、统一旅行合同，同时保持当前结果

**用户结果**

当前马尔代夫入口、结果卡和自然语言修改保持不变，但内部不再把它当成唯一旅行结构。

**实施内容**

- 增加 `TravelIntent`、同行者/同行组、固定活动、层级地点和条件合同；
- 增加 RequirementGraph、OfferCatalog/OfferGraph、PlanGraph 和 `PlanSolver` 接口；
- 增加覆盖人员、组件、日期和计价单位的 `PriceContract`；
- 用兼容适配器把当前 `PackageIntent`、库存和候选映射到新模型；
- 当前 `PackagePlanner` 保留为单目的地固定结构快路径。

**完成标准**

同一保存来源输入在新旧路径上得到相同选中组件、人民币总价、条件结果和来源引用；正式入口可以从新合同调用现有求解器。

### 二、用三种旅行结构验证领域模型

**用户结果**

TripChord 不再只会表达单目的地整团往返，开始具备多城市和分组同行的真实领域基础。

**实施内容**

使用固定来源数据，通过同一中央流程运行：

1. 当前单目的地灵活日期往返；
2. 多城市异地进出，并包含固定时间活动；
3. 两地出发后汇合、部分活动不全员参加、部分人提前离开。

这一步不做第二次耗时数天的真实平台全窗口查询。固定数据用于快速暴露领域模型问题，不冒充实时来源证明。

**完成标准**

三个场景共用同一种需求、报价、求解和最终行程合同；每位同行者时间地点连续，共享房价和套票只计算一次；新增结构不需要复制中央工作流或加入城市专用分支。

### 三、统一组合求解与方案取舍

**用户结果**

复杂场景中的城市顺序、活动时间、房间、同行分组和总费用能够一起求解；用户偏好不同会得到不同但可解释的答案。

**实施内容**

- 当前精确组合器继续作为简单快路径；
- 用 CP-SAT 处理有限候选下的活动时间窗、容量、人员分合流和锁定组件；
- 对小型库存做暴力枚举，核对可行性、最优状态和 Pareto 集合；
- 用户偏好明确时选一份；偏好不足时从同一批来源给出三种代表方案；
- RCSP 只有在代表性 OfferGraph 上明显优于当前路径后才实现。

**完成标准**

快路径与 CP-SAT 在可枚举小型数据上命中相同的可行最优解和 Pareto 集；三种默认方案不重复、理由可核对，并且不为每种答案重新查询来源。

### 四、让 Multi-Agent、上下文、记忆和 Skill 按需工作

**用户结果**

简单需求直接得到结果，复杂取舍才使用专业模型；更多日期和平台不会让 Agent 数量或模型等待线性增加。

**实施内容**

- 实现确定性 Agent Need Router；
- 需求歧义、来源身份冲突、Pareto 取舍、特殊旅行风险和复杂修改分别触发相关角色；
- Agent 只接收相关子图、有限候选、适用偏好和版本化 Skill；
- 日期生成、平台查询、金额、求解、最终核对继续由程序完成；
- 长期记忆只写入用户明确确认的稳定偏好。

**完成标准**

简单场景跳过模型后仍得到同一方案；存在真实取舍的盲测中，按需角色相对单模型和固定全团队改善答案，并且新增耗时与调用可以解释。每个被调用角色都能说明自己改变了什么判断。

### 五、增加一个小型真实扩展

**用户结果**

用户第一次从实时来源获得包含新组件或新旅行结构的完整方案，而不是只有离线架构证明。

**实施内容**

选择一个有代表性但查询范围很小的扩展，例如一段铁路或一个固定活动；只查询有限日期和来源，并接入同一人民币总价、条件、Pareto 和行程卡。

**完成标准**

新增类型只增加组件、来源适配或旅行 Skill，不修改中央工作流；真实来源结果和失败边界可追溯；查询、比较和建议形成一条短小的端到端链。

### 六、对外提供完整 TripChord 能力

**用户结果**

聊天助手、桌面工具或自动化环境可以创建旅行规划、稍后取回结果并继续修改，而不需要知道 TripChord 内部有哪些角色。

**实施内容**

- 提供创建规划、查询进度、修改行程和读取结果四个粗粒度接口；
- 优先支持 MCP，同时保留现有 API 和原生界面；
- 所有入口共享同一个 `TripRun`、偏好、来源快照和 PlanVersion；
- Oh My Pi、DeepSeek Harness 等宿主只负责交互与展示。

**完成标准**

外部客户端可以创建任务、断开后按任务 ID 取回结果，再提交“保留航班，只换酒店”；未受影响组件不重复搜索，也不会产生第二份权威旅行状态。

## 当前不进入主线的内容

- 不迁移到 LangGraph、CrewAI、AutoGen 或其他 Runtime；
- 不为每一种旅行增加固定 Agent 或复制工作流；
- 不做第二次耗时数天的全窗口真实需求来证明领域模型；
- 不先建设手机端、安装器、图数据库或通用分布式基础设施；
- 不用测试数、Agent 数、框架数或平台数代替最终旅行结果；
- 不做付款、下单、库存锁定或预订管理。

这些内容只有在真实主线证明它们已经成为阻碍时才重新排期。

## 什么时候重新讨论架构

- 新旅行类型反复无法表示成组件、条件、价格合同或图依赖；
- 新合同不能等价承接当前真实链；
- CP-SAT 在代表性有限候选上成为新的主要瓶颈，而专用求解器在同数据基准明显更好；
- 现有 Runtime 直接阻碍按需 Agent、任务继续或单一状态，且局部替换无法解决；
- 真实对照表明按需 Multi-Agent 没有提高取舍质量，新增耗时反而更大。

在出现这些事实前，下一步就是实施第一阶段，而不是继续比较框架。
