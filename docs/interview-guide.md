# TripChord 架构面试指南

这份文档只讲产品架构、技术取舍和证据边界，不包含现场演示流程或历史 Round 流水账。

## 一句话命题

TripChord 接收一个带日期窗口、同行人数和偏好的旅行需求，枚举合法日期，在成功覆盖且可比的已连接来源中，输出一份满足硬约束、完整人民币同行总价最低的最终行程。

“最低”只在本轮成功覆盖的来源内成立；不宣称全网最低、库存锁定、最终成交价、生产采用或自动下单。

## 端到端数据流

```text
用户需求
  → 需求理解与偏好解析
  → 确定性枚举完整日期空间
  → 固定有界日期 worker / provider lane 并行查询
  → 回执归一化与证据比较
  → 候选池与最终日期选择
  → 硬约束校验、风险审查、必要时局部修复
  → 确定性重验与安全发布
  → 一份 final plan
```

### 1. 输入冻结

需求理解 Agent 把自然语言转换为目的地、出发/返程窗口、晚数范围、同行人、房间、预算、交通偏好和硬约束。

用户明确写出的条件优先于历史偏好和模型推断；冲突或无法安全解释的字段不能由模型猜测。

同行人结构包含成人、儿童、婴儿、儿童年龄和房间数。总价比较以实际 party 为单位，而不是默认“两位成人”。现有 OTA 适配器遇到未覆盖的混合同行人会明确拒绝，不静默错算。

### 2. 完整日期空间

日期全集由确定性枚举器生成，当前支持边界内最多 400 个合法日期对。LLM 不负责决定搜索空间，也不会为每个日期创建一个模型 Agent。

日期空间由固定 3 个 worker 执行；worker 是受 provider、垂类、权限、并发和超时合同约束的非 LLM worker。

对每个查询计算稳定指纹：provider、垂类、路线、出发/返程日期、完整 party、房间、币种和住宿计划均参与指纹。

同一运行内的跨日期 singleflight 共享相同指纹的成功或类型化失败，只有新指纹占用 provider lane。最终发布前的刷新显式绕过去重，保证重新查询。

在 66 个日期组合的确定性集成路径中，858 个逻辑查询归并为 648 个唯一采集，去掉 210 个重复查询。

静态计划和运行时最后启动时间为 290 秒，加上 240 秒保守执行/收尾预算，内部调度边界为 530 秒。

这证明的是项目内部的并行、去重和预算契约，不是真实 OTA 网络在十分钟内完成的证明。平台批量/range 只是可选增强，当前性能路径不依赖平台提供批量接口。

## 为什么采用 multi-agent

TripChord 不是把一个大 prompt 拆成很多“会聊天的角色”，而是把不确定的决策和确定的事实执行分开。

模型角色拥有受限的提案权：理解需求、安排查询波次、策展候选、识别软风险和提出修复建议。

确定性组件拥有事实和安全权：枚举日期、调用只读来源、计算人民币总价、检查身份/人数/新鲜度、执行修复、重验和发布。

这种分工让不同工作使用不同上下文、工具权限和失败策略，也让任何一个模型的错误不能直接改变价格、授权或最终硬约束。

## 角色职责

| 角色/组件 | 负责什么 | 不能做什么 |
|---|---|---|
| 需求理解 Agent | 解析需求、冲突、硬约束和偏好候选 | 不能改写用户硬约束 |
| 日期枚举器 | 生成全部合法日期对并计算晚数 | 不由 LLM 扩大或缩小全集 |
| Source workers | 查询交通、住宿和接驳来源 | 不能下单、支付或改变预算 |
| Search Supervisor | 在能力检查后提出查询波次与依赖 | 不能突破白名单、并发或超时 |
| Quote normalizer | 归一产品身份、税费、币种、party total、新鲜度 | 不能用缺失字段填充价格 |
| Candidate Curator | 在可比证据上形成有限候选 | 不能伪造报价或发布多份最终方案 |
| Hard Verifier | 检查日期、人数、房间、路线、衔接、预算和证据 | 不能被模型覆盖 |
| Risk Reviewer | 发现软风险和信息缺口 | 不能否决确定性事实后再强行发布 |
| Repair Advisor | 提出换选、补查或澄清策略 | 不能直接修改已验证事实 |
| Repair Executor | 按确定性规则执行允许的局部修复 | 不能扩大权限或搜索范围 |
| ReVerifier / Safety Gate | 重新校验并决定是否可发布 | 不能把缺证据变成已验证 |
| Preference Memory | 管理显式确认的稳定偏好 | 不能保存实时价格和库存 |

Source worker 不是 LLM Agent。把浏览器任务包装成 Agent 数会夸大模型参与度。

只有最终选中日期的候选评议、风险审查、修复建议和解释需要模型角色；日期全集阶段主要是确定性并行采集。

## LLM 与确定性系统的边界

### LLM 适合

- 从自然语言提取语义和软偏好；
- 在允许的查询任务中安排优先级和依赖；
- 比较有证据支撑的候选；
- 发现“交通衔接不舒服”“住宿位置偏远”等软风险；
- 提出替代方案、补查策略和面向用户的解释。

### 确定性代码必须负责

- 合法日期、晚数和完整日期空间；
- party、房间、儿童年龄和总价计算；
- 税费、服务费、行李/早餐等产品组成；
- 稳定产品身份、来源、采集时间和新鲜度；
- 去重、并发上限、超时、权限和只读工具合同；
- 硬预算、时间冲突、住宿衔接和路线可行性；
- 修复执行、重新采集、证据绑定和安全发布。

模型可以提出“更换候选”，但不能说“金额大概正确”。Verifier 失败时，模型的自信不能覆盖失败。

## 价格命题与证据约束

这里的“证据约束”不是要求模型写理由，而是让最终价格和方案必须由可追溯的当前回执支撑。

进入最终排序的报价必须至少满足：来源成功覆盖、日期与 party 匹配、产品身份稳定、币种为人民币、同行总价完整、税费口径可比、报价仍新鲜。

缺税费、缺完整 party total、缺产品身份、来源未成功覆盖或报价过期时，候选不能进入“最低价”排序；系统应返回待确认/阻断，不填零、不拿旧价格补齐。

证据记录来源、采集时间、稳定身份、回执摘要和哈希。原始浏览器数据属于私有运行证据，不应因为面试文档而公开用户环境或登录信息。

## 最终方案而不是候选列表

内部可以保留多个候选、排序诊断和被拒理由，但用户最终只收到一份 final plan。

选择目标是：先满足硬约束，再在成功覆盖的可比来源中比较完整人民币同行总价；同价时再按用户明示偏好和确定性排序规则择优。

“完整人民币同行总价”意味着按实际成人/儿童/婴儿、房间和产品组成计算，不按单人展示价或默认人数比较。

## 偏好记忆边界

只有用户明确确认的稳定偏好才可形成长期记忆候选，例如“住宿不能简陋或偏僻”“优先品质与价格平衡”。

记忆按用户、行程、会话和租户作用域隔离，带来源、版本、时间、TTL、隐私标记和可撤销能力。

本次请求中的明确选择覆盖历史偏好；偏好候选默认需要用户确认，不能由模型或发布门自动写入长期记忆。

实时价格、库存、余位、班次、可订状态和本次平台回执永不写入长期记忆，也不能通过 RAG 作为下一次的当前事实。

当前 RAG 使用 BM25 检索偏好、历史决策/修复、平台能力和仍新鲜的非实时证据；实时事实只能来自本次工具回执。

## 上下文工程与独立审查

Query、Planner、Repair 使用分开的 Context Pack 预算。构建顺序是：当前请求、不可裁剪的 Verifier 证据、其他新鲜证据、作用域过滤后的偏好记忆、后续工具观察预留空间。

工具回执以不可信数据放回上下文；过大的回执只保留明确预览、原始字节数和摘要哈希。当前请求或关键拒绝理由放不下时失败关闭，而不是静默截断。

模型只提出结构化意见。Hard Verifier、ReVerifier 和 Safety Gate 对金额、身份、授权和发布拥有独立权威，避免同一个模型既提出方案又给自己验收。

## 失败与局部恢复

局部恢复是配套能力，不是产品主命题。它的意义是一次来源、一个住宿或一个接驳发生变化时，不必盲目重做已经有效的全部工作。

系统先识别受影响的候选和依赖，再仅重查受影响部分；保留未受影响的已验证事实，之后重新执行确定性校验和发布门。

如果恢复后缺少完整总价、必要来源覆盖或新鲜证据，结果仍为待确认/阻断。局部恢复不等于自动修复成功，也不等于全局最低价仍成立。

## 关键技术权衡

### 完整日期空间 vs 只搜热门日期

完整枚举支持“窗口内 4–7 天”的真实最优问题；代价是查询量大。因此使用固定 worker、provider lane 和跨日期 singleflight，而不是让模型随意丢日期。

### 并行 vs 平台限速

日期和来源可并行，但浏览器 lease、平台垂类和 provider lane 仍有独立上限。模型并发增加不会带动 Chrome 或某个平台无限扩容。

### singleflight vs 实时刷新

同一运行内相同采集只做一次，降低重复查询；最终发布刷新显式绕过去重，避免把旧回执误当新价格。

### 灵活 Agent vs 可审计预算

模型可以做局部排序和修复决策，但 Agent 数量、模板、工具和停止条件由确定性控制器限定。避免模型自我复制带来的成本、死循环和权限扩张。

### BM25 vs 向量库

当前记忆字段少且结构化，BM25 易解释、易复算、便于安全过滤。未来可以增加混合/向量检索，但必须保留作用域、TTL、隐私和实时数据禁入门。

### 本地优先 vs 外部模型

默认 `MODEL_PROVIDER=none`，不会自动产生付费调用。显式配置兼容网关后，结构化需求、证据摘要和获准工具回执才进入模型；Cookie、凭据、Chrome profile 和 pairing secret 不进入模型。

## 当前可以说什么

- 已实现固定日期 worker、provider lane、跨日期 singleflight、结构化 party、报价归一、硬校验、局部修复、重验和只读浏览器路径。
- 66 个日期组合的内部集成路径可重复得到 858→648，去重 210，内部边界 290s+240s=530s。
- 主应用已具备模型路由和多阶段角色接线；模型是否实际参与必须看该次运行的非 scripted trace。
- 本地测试、fixture、benchmark 和历史模型/浏览器运行可以分别证明对应层级的行为。

## 当前不能说什么

- 不能说真实 OTA 网络在十分钟内完成；530 秒是内部调度/执行预算。
- 不能说全网最低价；只能说成功覆盖且可比的已连接来源内最低。
- 不能说所有成人/儿童/婴儿混合同行人都已通过真实 OTA 适配器。
- 不能把模型接线、回放或单测说成生产用户、商业采用或完整 Done-Gate 成功。
- 不能说平台 range/batch 已经具备；当前没有生产批量适配器。
- 不能说自动下单、支付、锁库存、修改或取消预订。

## 高频追问与推荐回答

### 为什么不是一个聊天模型？

单模型可以生成一条看似合理的路线，但难以同时管理完整日期空间、多个来源的实时回执、不同工具权限、价格可比性和失败关闭。TripChord 把模型用于语义决策，把事实、金额、权限和发布门交给可复算组件；多 Agent 的价值是职责隔离和上下文隔离，不是 Agent 数量越多越好。

### 这是不是“硬代码包了一层 LLM”？

不是。模型在受限阶段拥有真实决策权：可以选择查询优先级、策展候选、提出修复策略。只是它不能篡改事实不变量。安全系统的关键不是让模型拥有所有权限，而是让模型的决策能被验证、拒绝和重做。

### 失败为什么不直接重跑全部？

全部重跑简单但慢、贵，还会重复触碰平台。依赖图允许定位受影响部分；局部重查后必须重新过同一套硬校验。无法补齐证据时宁可阻断，也不包装成最佳方案。

### 记忆会不会污染实时最低价？

不会。记忆只保存显式确认的稳定偏好和非实时能力；价格、库存、班次和可订状态不进长期记忆/RAG。每次最终方案都必须从本轮来源回执重新计算。

### 这些性能数字来自哪里？

来自可重复的 66 组合确定性集成路径：逻辑查询、唯一采集、去重数量和内部启动预算均可审计。它们不代表供应商响应时间，也不代表真实 OTA 覆盖完成率。

### 现在是否已经真实跑通完整多 Agent OTA？

准确回答是：主应用已完成模型路由和真实浏览器路径接线，并有有限的真实模型/浏览器运行证据；当前公开材料不能把这些升级为整套 OTA Done-Gate 成功。真实运行仍可能被登录、验证码、DOM 漂移、限速、报价时效或来源缺证据阻断。
