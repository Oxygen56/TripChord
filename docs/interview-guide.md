# TripChord 架构面试指南

这份指南用于讲清 TripChord 的产品价值、问题定义、架构设计和工程取舍。重点不是展示多少个 Agent，而是说明：为什么真实旅行规划需要这套系统，以及每一层如何共同产出一份可信的最终行程。

## 30 秒项目介绍

> TripChord 是一个面向自由行的多 Agent 规划系统。用户只需给出出发地、目的地、灵活日期、旅行时长、同行人数和偏好，系统会枚举合法日期组合，并行查询交通、住宿和接驳来源；在来源支持且信息完整时，统一比较人民币同行总价并只交付一份满足硬条件的首选行程，否则返回零方案和明确缺口。它的核心设计是让 LLM 负责需求理解、语义取舍和风险判断，让确定性系统负责日期、金额、产品身份、权限与最终发布。

## 90 秒产品故事

用户真正提出的通常不是一个精确查询，而是：

> 我想在 8 月 20 日到 9 月 10 日之间从杭州去马尔代夫，旅行 4–7 天；这次是 2 位成人、1 间房，住宿不要简陋或偏僻，希望品质和价格平衡。

这个需求会产生大量日期组合，还要把不同平台上的机票、酒店和接驳拼成同一条可行链路。平台展示的数字可能是单人价、每晚价、未税价或起价；最便宜的单项也可能因为航班时间、入住区间或接驳班次无法组合。

TripChord 先把自然语言转换成硬条件与软偏好，再由程序生成日期空间。交通、住宿和接驳来源并行查询，结果统一绑定到确切日期、产品、人数、税费和采集时间。系统组合候选、检查衔接和完整总价；多个专业 Agent 分别处理可比性、候选选择、风险和修复，最后由独立的确定性安全门决定能否发布。

用户看到的是一份完整答案，不是一堆还要自己继续筛选的链接。若当前结果不足以支撑完整总价，系统会明确说明缺口，而不是让模型猜一个答案。

## 问题为什么难

### 1. 搜索空间是组合型的

“三周内旅行 4–7 天”不是一个日期，而是一组出发/返程组合。若先凭经验抽样，很可能在第一步就漏掉真正更合适的日期。

### 2. 不同来源的价格不能直接比较

同一个页面数字可能代表单人、单程、单晚、未税或最低起价。只有先统一人数、房间、日期、产品身份、税费和币种，价格排序才有意义。

### 3. 最便宜单项不等于最优行程

便宜航班可能错过接驳，便宜酒店可能位置偏远，分开最优的组件未必能形成可行的整体。TripChord 优化的是完整行程，而不是三个孤立搜索列表。

### 4. 实时事实会过期，用户偏好却要长期存在

“需要早餐”可以记住，“某酒店今天 ¥1,200”不能记成下次的当前价格。系统必须把稳定偏好与实时事实分开存储和检索。

### 5. 长任务会失败、超时和变化

多个平台、多个日期和多个垂类同时运行，任何一步都可能超时、限流或页面变化。系统既要并行提速，也要保留失败语义、取消能力和恢复边界。

## 核心架构

```text
自然语言需求与已确认偏好
  → 结构化旅行意图
  → 确定性日期空间
  → 固定 worker + 来源级并发查询
  → 报价归一与产品身份绑定
  → 完整行程候选生成
  → 多 Agent 语义评议与风险审查
  → 确定性验证、修复执行与重验
  → Safety Gate
  → 一份 FinalPlan
```

这套架构刻意把系统分成两部分：

- **概率型决策层**：理解语言、处理偏好、发现软风险、提出修复；
- **确定性权威层**：计算日期和金额、控制工具权限、绑定来源身份、执行修改、验证并发布。

前者提供智能，后者提供可以追问和复算的工程边界。

## 六个项目亮点

### 1. 完整旅行优化，而不是聊天式推荐

TripChord 把航班、住宿和接驳放进同一个约束问题。先保证路线、日期、人数和衔接成立，再比较完整人民币同行总价和用户偏好。

### 2. 灵活日期的确定性搜索

日期全集由程序生成，LLM 只能在冻结空间内建议精查顺序。固定 worker、平台独立并发和跨日期去重，使搜索规模扩大时不会等比例复制模型或重复访问来源。

### 3. Multi-Agent 有真实权限边界

不同 Agent 使用逻辑隔离的上下文、工具白名单、输出 schema 和失败策略。候选选择者不能修改价格，风险审查者不继承选择理由，修复者不能给自己的修改做最终验收；它们共享模型路由和进程，因此仍有共同故障域。

### 4. 价格完整性是一等领域模型

系统显式建模 price basis、币种、party total、税费、来源、新鲜度和产品身份。非完整人民币同行总价可以参与诊断，但不能进入最终价格最优声明。

### 5. 个性化记忆不污染实时事实

只有用户确认的稳定偏好可以长期保存，并支持作用域、覆盖、过期和撤销。价格、库存、余位、班次和可订状态永远从当前运行重新取得。

### 6. 长任务优化关注“少做无效工作”

TripChord 使用并行查询、singleflight、失败共享、进程内阶段进度和最终组件刷新。性能优化的重点不是无限并发，而是减少重复访问、模型调用和不必要的全局重跑；跨重启持久恢复仍是 Beta 目标。

## 每个 Agent 的必要性

角色拆分代表当前设计中的独立责任，并不意味着角色数量越多越先进。它们共享类型化运行时，但拥有不同的上下文和权限。

| Agent | 负责什么 | 为什么不能简单混在一起 |
| --- | --- | --- |
| `Context` | 解析需求、冲突和偏好候选 | 用户事实必须在看到搜索结果前冻结，避免反向迎合候选 |
| `Query Strategist` | 在合法日期空间和预算内提出精查顺序 | 搜索覆盖与最终选品是不同目标 |
| `Search Supervisor` | 安排已获准查询的依赖与波次 | 只能调度任务，不能扩大权限或修改用户条件 |
| `Evidence Arbiter` | 判断产品身份和价格是否可比 | 先建立事实口径，再谈更喜欢哪个方案 |
| `Candidate Curator` | 在合格候选中结合总价和偏好提出首选 | 拥有语义取舍权，但没有创造报价的权力 |
| `Risk Critic` | 独立检查中转、入住、位置和接驳等软风险 | 不读取策展者的选择理由，降低确认偏误 |
| `Repair Strategist` | 根据失败原因提出换选、补查或询问 | 只提出修复，不直接修改已验证事实 |
| `ReCritic` | 检查修复后是否引入新风险 | 修复提出者不能同时完成自己的软风险验收 |
| `Event Diagnoser` | 判断输入的价格、班次或库存变化事件影响哪些组件 | 把影响定位与重规划分开；当前不代表已接供应商实时推送 |
| `Orchestrator` | 汇总各角色输出并提出业务状态建议 | 统一语义决策，但不能越过确定性 Safety Gate |
| `Explanation` | 将已批准事实组织成用户可读说明 | 可以改变表达，不能新增旅行事实 |
| `Memory Curator` | 提出待用户确认的长期偏好候选 | 一次规划的结果不能直接写成长期用户画像 |

与模型 Agent 同样重要的是非 LLM 组件：日期枚举器、Source workers、报价归一器、Candidate Generator、Hard Verifier、Repair Executor、ReVerifier 和 Safety Gate。它们不是“辅助代码”，而是系统可信度的权威层。

## 关键技术取舍

### Multi-Agent vs. 单一模型

单一模型实现简单，但会把需求、搜索、选品、审查、修复和解释混进同一个上下文，也很难为不同阶段配置不同工具权限。TripChord 选择角色隔离，是为了降低上下文污染和权限耦合。

这仍是一项需要持续验证的设计：项目应记录各角色的调用次数、成本、延迟、拒绝原因和结果变化，并通过消融实验判断哪些角色应常驻、条件触发或合并。当前不能仅凭角色表宣称 Multi-Agent 一定比单模型质量更高。

### 完整日期空间 vs. 日期抽样

抽样更快，但无法回答“窗口内哪组日期更优”。TripChord 选择由程序生成合法全集，再用固定 worker、查询预算和去重控制执行成本。若时间预算不足，系统应明确拒绝全窗口最优声明，而不是静默只查一部分。

### 探索复用 vs. 最终价格新鲜度

探索阶段允许相同查询共享结果，降低平台访问量；最终发布前必须刷新被选中组件。这样既减少重复工作，又不把一次早期缓存直接当成最终当前价格。

### 自研运行时 vs. LangGraph

当前不全面迁移 LangGraph。TripChord 已经拥有类型化任务图、依赖校验、有界并发、工具权限、结构化回执和领域 Safety Gate；重写这些能力会带来双状态语义和大面积回归风险。

LangGraph 真正有价值的部分是模型子图 checkpoint、interrupt 和状态调试。只有某个模型子流程确实需要跨重启暂停恢复、人工介入或复杂循环，并且 shadow 试验能证明没有重复外部调用、没有过期价格复用、没有结果退化时，才局部采用。

跨进程、跨机器和小时级可靠执行属于业务工作流问题。TripChord 的优先路线是先统一 PostgreSQL 持久化任务控制面；需求进一步扩大后，再评估 Temporal 作为外层工作流。框架不会接管报价新鲜度、浏览器权限或最终发布规则。

### 自然语言解释 vs. 事实安全

Explanation Agent 不自由生成事实，而是从服务端批准的 claim 目录中选择和排序。这牺牲了一部分表达自由，换来解释内容与最终组件的一致性。

### BM25 vs. 向量检索

当前偏好字段数量有限、结构明确，BM25 和规则过滤更容易解释、复算和做隐私控制。以后可以加入向量召回，但它只能扩展检索，不能绕过作用域、TTL 和实时事实禁入门。

## 上下文工程

TripChord 不把全部需求、网页内容、候选和历史记忆发给每个 Agent。系统按角色构建 Context Pack：

1. 当前请求和不可裁剪的硬条件；
2. 与该角色任务相关的新鲜来源摘要；
3. 必须保留的验证失败原因；
4. 作用域内、仍有效的确认偏好；
5. 为后续工具观察预留的预算。

大型工具结果只保留必要预览、摘要和哈希引用；上下文不足以容纳关键事实时失败关闭。`Risk Critic` 不继承 `Candidate Curator` 的选择理由，修复后的审查也由另一个角色完成，避免把“独立审查”只写在 prompt 里。

## 记忆设计

TripChord 将记忆分成三类：

- **当前请求事实**：只对本次运行有效，优先级最高；
- **稳定偏好**：用户确认后长期保存，可撤销、过期和按作用域覆盖；
- **实时来源事实**：价格、库存、班次和可订状态，只能通过当前工具回执使用。

`Memory Curator` 只能提出待确认候选，不能自动写入长期记忆。RAG 的职责是恢复“用户喜欢什么”，不是恢复“上次多少钱”。

## 性能与工程化

内部 66 日期组合的确定性集成基准会产生 858 个逻辑查询，经跨日期指纹归并为 648 个唯一采集，去掉 210 个重复查询。该基准验证的是调度、去重和失败共享逻辑；真实延迟还受平台响应、登录、限流和网页稳定性影响。

成熟版本需要持续观测：

- 端到端和各来源 p50/p95 延迟；
- 唯一采集数、去重率和缓存命中；
- 每个模型角色的 token、成本和失败率；
- 候选在各验证门的淘汰原因；
- 最终发布率、人工确认率与重新规划率；
- 任务取消、重启恢复和孤儿进程状态。

这些指标用来定位产品问题，不能单独代替真实用户是否获得满意行程。

## 当前成熟度与路线

TripChord 当前处于 Alpha：核心规划、灵活日期、跨来源报价归一、多角色决策、偏好记忆、变化处理和只读浏览器路径已经形成；标准实时入口、持久化任务控制面、复杂同行人覆盖、来源稳定性和发布运维仍需完善。

### 走向 Beta

- 让标准入口稳定完成限定范围内的真实旅行规划；
- 将任务状态、租约、幂等、取消和阶段检查点统一到 PostgreSQL；
- 建立端到端耗时、成本、失败与 Agent 边际价值观测；
- 明确同行人、来源和错误语义的支持矩阵。

### 走向 RC

- 完成多进程 claim、取消、恢复和浏览器故障测试；
- 对数据库、API schema 和运行中任务提供兼容迁移；
- 在固定支持范围内重复形成同口径唯一最终方案；
- 建立不可变发布候选和完整安全检查。

### 走向 1.0

- 可安装、升级、回滚；
- 有明确的服务目标、数据保留、安全和降级策略；
- 有真实用户运行数据证明结果质量与可靠性；
- 平台变化可以被监控并有恢复路径。

## 高频追问与回答

### TripChord 和普通旅行聊天机器人有什么本质区别？

普通聊天机器人主要生成建议；TripChord 建立并执行一个可验证的旅行优化过程。它搜索日期空间、查询当前来源、统一总价口径、组合完整行程，并在发布前通过独立验证。自然语言只是入口和解释层，不是事实来源。

### 为什么不直接让一个强模型调用所有工具？

模型越强，越需要清楚定义哪些错误可以容忍、哪些权限不能拥有。单模型会共享同一上下文和工具面，难以做到选择、审查、修复相互独立。TripChord 用多个受限角色获得专业分工，再由确定性层兜住金额和权限。

### 每个 Agent 有没有自己的 Skill、插件或工具？

有业务能力配置，但不是给所有角色安装一批通用插件。每个 Agent 都有独立目标、Context Pack、类型化工具白名单、输出 schema 和本地校验器。例如 Evidence Arbiter 只能检查归一报价，Candidate Curator 只能查看冻结候选，Repair Strategist 只能查看候选与验证失败。当前没有外部插件运行时；旅行能力优先做成可测试的来源适配器和领域工具，避免插件绕过产品权限。

### Multi-Agent 是否真的比单 Agent 更好？

当前代码证明了角色、上下文和权限隔离已经接线，但角色表本身不能证明质量更高。严谨做法是对真实任务做消融：比较结果质量、阻断率、延迟和成本，再决定哪些角色常驻或按风险触发。

### 为什么不直接使用 LangGraph？

TripChord 的核心难点是旅行领域合同，而不是缺图形 DSL。全面迁移不会自动解决报价新鲜度、浏览器租约、平台限流和总价校验。保留自研内核并给 LangGraph 设置明确采用门槛，比为了框架标签重写系统更能体现工程判断。

### 怎样保证“最佳”不是模型主观判断？

硬条件、完整人民币同行总价和价格排序由程序计算。模型只在合格候选中处理显式偏好和软风险；最终结果仍需 Safety Gate 重新检查。对外的“最佳”始终限定在本次成功覆盖且可比的来源内。

### 如果一个平台失败，会不会把其他平台结果当全网最低？

不会。失败来源会作为覆盖缺口保留。系统可以在剩余成功且可比的来源中给出首选，但必须收窄声明，不能把未查询的平台算成已经比较过。

### 为什么用户只看到一个方案？

用户交给系统的是决策任务，而不是搜索结果整理任务。内部候选用于竞争和诊断；对外发布一份最终方案，可以让产品对选择负责。证据不足时宁可不发布，也不把不确定性转嫁成几十个候选。

### 如何避免长期记忆污染当前价格？

偏好和实时事实使用不同 schema 与准入门。只有确认过的稳定偏好可以进入长期记忆；当前价格必须来自带时间戳和身份绑定的本次来源回执，发布前还会刷新选中组件。

### 最大的工程短板是什么？

不是缺少更多 Agent，而是标准实时执行与持久化控制面还未达到成熟产品要求：任务状态仍需统一、复杂同行人和来源覆盖要扩大、真实延迟与质量指标要持续积累。这也是从 Alpha 走向 Beta 的主线。

### 这个项目最能体现高级工程能力的地方是什么？

不是“调用了很多模型”，而是将一个开放式用户需求拆成组合搜索、异构数据归一、受限语义决策和确定性发布四类问题，并为并发、记忆、权限、失败和框架采用做了明确边界。每个设计都能说明放弃了什么、保护了什么，以及如何验证。

## 简历与项目页建议

推荐把 TripChord 定位为：

> **面向灵活日期自由行的多 Agent 旅行决策系统**：将自然语言需求转化为跨交通、住宿和接驳来源的完整行程优化；通过确定性日期搜索、人民币同行总价归一、角色化上下文与权限、偏好记忆和最终安全门，输出一份可核对的首选方案。

三个最值得展开的项目亮点：

1. **问题建模**：从搜索单项升级为完整行程的组合约束优化；
2. **Agent 架构**：模型负责语义判断，确定性层掌握事实和发布权；
3. **工程化**：跨日期并发与去重、上下文隔离、实时事实与长期记忆分离、失败恢复和框架采用门槛。

## 声明边界
