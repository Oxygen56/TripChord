# TripChord 架构决策记录

这份文档记录会改变 TripChord 产品职责、核心算法、Agent 分工或长期维护方式的重要决定。它不是开发流水账，也不以“采用了多少框架”为成果。每项决定都要说明：解决什么问题、选择了什么、为什么、哪些方案被否决、当前证据支持到哪一层，以及什么新事实会迫使我们重新评估。

目前的结论是：TripChord 保持为一个可以独立使用的复杂自由行决策 Agent，自己负责整理平台结果、组合完整行程和选择最终方案。2.0 已在七轮范围受控场景中覆盖单人或多人、单城或多城、异地进出、分地出发后汇合以及固定活动；1.0 单出发地/单目的地往返作为兼容快路径和历史基线保留。模型只处理语言理解和确实需要判断的取舍；日期、金额、人员连续性和行程能否成立由程序计算。其他 AI 应用可以通过统一接口调用完整的 TripChord，但不会接管它的内部流程。现有生产运行方式暂时不更换。逐轮证据见 [2.0 公共验收](v2.0-acceptance.md)。

## 怎样记录重要决策

只有满足下面任一条件的选择才进入本文档：

- 改变 TripChord 对用户承诺的最终结果；
- 改变 LLM、确定性程序和真实来源之间的责任边界；
- 引入或移除会长期影响核心运行方式的框架；
- 改变规划、记忆、增量修改或对外集成的事实来源；
- 推翻已经公开说明过的架构选择。

每项决策使用以下状态之一：

- **已确认**：方向已经确定，但实现或真实验证尚未完成；
- **已验证**：已经有可复现运行支持该决定；
- **保留观察**：当前不进入主架构，但保留清楚的重开条件；
- **已被取代**：新决定已经替换旧决定，并链接替代原因。

文档、测试或框架样例本身不是成功证明。涉及真实旅行能力时，仍以真实来源或明确标注的历史来源回放为准。

## D001：TripChord 是可以独立使用的旅行规划 Agent

**状态：已确认；核心流程已有真实旅行查询记录和可复现回放。决定日期：2026-08-23。**

### 决定

TripChord 首先是一个可以独立使用的旅行规划产品，而不是一套要求用户自行组装的 Agent 开发框架。用户提交一次旅行需求后，它负责完成从理解需求到给出最终方案的完整过程，不要求用户再安装或操作其他 Agent 平台。

一次完整规划包括：

1. 理解日期范围、出行天数、同行人数和用户在意的体验；
2. 查询交通、住宿和接驳信息，并把不同来源整理成可以比较的格式；
3. 计算这次所有人的总费用，并统一换算成人民币；
4. 排除日期冲突、衔接不上或不满足要求的方案；
5. 从剩余方案中选出最符合本次需求的一份；
6. 接受后续修改，并尽量保留不受影响的部分；
7. 记住用户确认过的长期偏好，但不把临时价格和库存当成偏好保存。

模型和 Agent 框架可以帮助 TripChord 理解语言、调用工具或安排执行顺序，但这些框架只是可替换的实现方式。无论以后更换哪种框架，上述旅行规划能力都必须继续由 TripChord 自己负责。

### 为什么这样设计

TripChord 真正解决的问题，不是让多个模型进行一段看起来复杂的对话，而是把来自不同平台、原本无法直接比较的交通和住宿产品，组合成一份确实可行的完整行程。

因此，日期是否合法、这次所有人的总费用是多少、航班和酒店能否衔接、方案是否满足用户要求，都必须由 TripChord 统一计算和检查。模型框架可以记录任务执行到了哪一步，但不能另外保存一套价格或最终答案，否则同一次旅行可能出现两份互相冲突的结果。

### 怎样接入其他应用

TripChord 可以被聊天助手、桌面应用或自动化工具调用，但外部应用只需要提交完整的旅行需求、查询进度和接收最终方案：

- 外部应用负责与用户交流和展示结果；
- TripChord 负责查询、计算、比较和最终选择；
- 外部应用不需要分别控制 TripChord 内部的多个 Agent；
- 用户直接使用 TripChord 时，也能获得同样完整的规划能力。

具体的接入方式记录在 [D004：接入其他 Agent 应用](#d004让其他-ai-应用调用-tripchord)。

### 什么时候重新评估

如果未来某个通用框架能够在不改变旅行结果、也不让同一行程出现两份互相冲突的数据的前提下，明显减少 TripChord 的维护工作，再考虑让它承担更多运行职责。在此之前，TripChord 保持完整、独立、可以单独验证。

## D002：用户目标决定什么叫最佳方案

**状态：已验证；多种默认答案已在范围受控当前/冻结场景实现。决定日期：2026-08-23。**

### 决定

TripChord 不把“最低价格”写成所有用户共用的固定目标，也不使用一个不可解释的全局加权分数。

一次需求先被整理为：

1. 不可妥协的条件；
2. 当前旅行中的个人优先顺序；
3. 可以接受的交换关系，例如为了直飞、酒店品质或节省时间最多愿意多花多少。

2.0 的行为是：用户已经表达清楚偏好时，系统只给一份个性化最佳方案；用户没有提供足够偏好时，系统从同一批可行候选中给出三份代表性答案。代表方案少于三种时诚实少给，不复制候选。

- **省钱优先**：满足基本品质要求后，这次所有人的人民币总费用更低；
- **综合均衡**：价格、时间、住宿品质与接驳便利性之间的代表性平衡点；
- **体验优先**：优先舒适度、位置和便利性，价格作为次要比较条件。

“体验优先”不等于无限预算，也不表示已经覆盖全网；它只在本次实际取得且可比较的候选中成立。

### 执行边界

- LLM 理解自然语言中的偏好与交换关系；
- 确定性程序生成合法日期、计算金额、过滤不可行项，并形成 Pareto 集合：集合中的每个方案都不存在另一个在所有关心维度上不差、且至少一项更好的替代方案；
- 三种答案复用同一轮来源查询和同一候选集合，不能各自重新跑一遍完整搜索；
- 当前请求始终可以覆盖长期偏好；只有用户确认过的稳定偏好可以写入记忆；
- 实时价格、库存和班次不能进入长期偏好记忆。

### 验证要求

实现后需要证明：同一批来源只查询一次；三种模式返回彼此有意义且不重复的代表方案；用户给出明确偏好时能稳定收敛为一份答案；选择一种模式后不会自动把本次偶然选择冒充长期偏好。

## D003：Multi-Agent 按任务需要动态运行

**状态：已验证；Need Router 已接入，按需触发在声明范围内成立。决定日期：2026-08-23。**

### 决定

Agent 数量不是目标。一个角色只有在需要独立的上下文、工具权限、模型判断或失败边界时才保留为 Agent；日期生成、金额计算、产品身份、不可妥协要求的检查和最终发布不能因为换了名称就被包装成 Agent。

目标角色包括：

- **需求与偏好 Agent**：理解当前请求和可接受的取舍；
- **平台搜索 Agent**：只在网页需要自主导航和判断时使用，可按平台或日期范围动态并行；
- **体验评价 Agent**：处理位置、品质、舒适度等不完全规则化的信息；
- **决策 Agent**：只在 Pareto 候选之间存在真实价值取舍时运行；
- **审查 Agent**：只在来源冲突、低置信度或高代价选择时触发并提出结构化异议；
- **表达与记忆 Agent**：生成中文说明并提出可能值得记住的偏好，不能自行确认长期记忆。

API 查询、日期枚举、并发调度、报价归一、组合优化、硬校验、增量重规划和发布仍是确定性组件。

一个日期组合只是待查询的工作项，不是一个 Agent。程序先生成完整合法日期空间，再由有界并发池分配查询；只有某个平台确实需要自主浏览、识别页面和处理交互时，才临时启动对应的平台搜索 Agent。

这里提到的业务方法、模型工具和外部接入不是同一层：

- **业务方法（Skill）** 说明怎样判断“位置方便”或怎样解释转机代价，只提供方法，不保存实时价格；
- **模型工具（Tool）** 让模型读取已确认需求、候选或程序校验结果，返回内容仍可被程序拒绝；
- **外部接入（Plugin / MCP）** 让其他 AI 应用调用完整的 TripChord，不参与一次行程内部的价格计算和选择。

| 模型角色 | 只接收的上下文 | 允许使用的能力 | 明确不能做什么 |
| --- | --- | --- | --- |
| 需求与偏好 | 当前请求、已确认的适用偏好 | 偏好读取、偏好候选提取 | 写入价格/库存，或自行确认长期记忆 |
| 平台搜索 | 一个来源与一组已分配日期 | 对应 provider/浏览器查询工具 | 改日期全集、比较全局最优或发布结果 |
| 体验评价 | 归一后的住宿/航班语义和来源片段 | 位置、舒适度、权益判断 Skill | 改金额、库存或可行性 |
| 决策 | 已通过校验的 Pareto 候选与用户优先顺序 | 有界候选比较 | 搜索新报价或接受不可行候选 |
| 条件审查 | 最终候选、来源引用和校验结果 | 只读反例与缺口检查 | 直接修改方案或用投票覆盖程序检查 |
| 表达与记忆 | 已发布方案与可说明的取舍 | 中文说明、偏好候选建议 | 新增任何来源事实或自动写入记忆 |

### 是否采用多模型投票与反复讨论

默认不采用模型投票、持续辩论或多审查者重复判断。多个相近模型读取相同来源时，很可能共享同一种错误；多数赞成也不能证明日期、价格或库存正确。

审查 Agent 的输出是可以核对的反例、风险或缺失证据，不是一张票。事实异议交给确定性检查，主观取舍才交给用户目标和模型判断。只有受控实验能证明多审查者在某类高风险语义问题上带来稳定收益时，才允许条件触发。

### 验证要求

对每个模型角色记录：是否改变最终有效方案、是否减少人工澄清或错误、增加多少模型调用和耗时。无法证明边际价值的角色应合并、按需触发或改成确定性函数。

### 当前对照结果

仓库的[单 Agent / Multi-Agent 公平基准](benchmark-agent-architectures.md)让两种架构使用同一套 12 个任务、同一 scripted model、同一只读工具和相同总预算。2026-08-23 的可复现结果如下：

| 指标 | 单 Agent | Multi-Agent |
| --- | ---: | ---: |
| 有效方案率 | 100% | 100% |
| 需要修改时的成功率 | 100% | 100% |
| 平均模型调用 | 4.25 | 10.25 |
| 平均工具调用 | 4.25 | 10.25 |
| 平均 token | 799 | 1,927 |

机器可读结果见 [`benchmarks/results/agent-architecture-v1.json`](../benchmarks/results/agent-architecture-v1.json)。这次对照证明了两套执行路径和统计口径可复现，也证明固定展开所有角色会增加调用；因为使用的是 scripted model，它不能证明真实模型下单 Agent 或 Multi-Agent 谁的答案更好。

因此当前决定不是删除 Multi-Agent，而是取消“每次都跑完整团队”：平台搜索可以按来源和日期动态并行；需求理解、体验判断、取舍和条件审查只在输入真正需要时实例化。要让某个角色进入默认主链，必须再用真实模型和未见旅行任务证明它带来的答案提升大于新增耗时与调用。

## D004：让其他 AI 应用调用 TripChord

**状态：已实现并完成范围受控验证；七轮 2.0 公共验收已记录。决定日期：2026-08-26。**

### 决定

TripChord 可以作为一项完整的旅行规划服务，被聊天助手、桌面 AI 或其他自动化应用调用。外部应用负责接收用户输入和展示结果，TripChord 负责搜索、比较、组合与最终选择。

接入采用 MCP。MCP 是一种让 AI 应用调用外部工具和服务的通用协议；使用它以后，外部应用不需要了解 TripChord 内部有多少模型角色，也不需要共享 TripChord 的数据库。

推荐的公共操作保持粗粒度：

- `create_plan`：创建规划任务并返回任务编号；
- `get_plan_status`：查询进度，不重新规划；
- `get_plan`：取得同一个 TripRun 的当前结构化方案；
- `modify_plan`：按新要求生成新版本和变化说明。

真实平台规划可能持续数分钟，因此创建任务和取得结果需要分开。MCP 只是现有异步任务接口的一层通用包装，不会另外创建一套任务或价格数据。

### 组合方式

```text
聊天助手 / 桌面 AI / 其他自动化应用
                  │
             MCP 通用接口
                  │
          TripChord 规划任务接口
                  │
       旅行规划内核与平台连接模块
```

外部应用可以附带一份简短使用说明，告诉模型何时调用 TripChord、怎样提交旅行需求以及怎样展示结果。这份说明不能负责价格计算、行程检查或最终选择。

本轮用 **Claude Code 2.1.245** 作为真实外部宿主，通过 stdio 完成创建、断开后恢复和酒店局部修改；再用官方 Python MCP SDK **1.29.1** 独立读取同一个 `run_id`。OpenCode 1.18.21 已确认可脚本化但未作为本次证据宿主；DeepSeek Harness 0.3.5 仅验证本机 GUI 安装，未声称已完成无头接入；Oh My Pi 未作为本轮宿主。机器可读证据见 [`i7-mcp-current-2026-08-26.json`](../benchmarks/results/i7-mcp-current-2026-08-26.json)。

TripChord 不把内部每个 Agent 暴露成单独工具。否则外部应用需要自己拼接搜索、价格和最终方案，反而破坏 TripChord 统一负责结果的产品边界。

### 验证要求

同一个任务通过 TripChord 原生入口和 MCP 入口运行时，应产生相同任务身份、相同最终方案和相同修改差异；MCP 入口不得增加一次完整重复搜索。

本轮范围受控结果：同一任务首次查询 6 个当前来源任务，外部宿主断开后只用 `get_plan_status`/`get_plan` 恢复，没有新增查询；“保留所有车次，只换共享酒店”只查询该住宿段 1 次，生成 v2 和差异。结果仍仅限 12306 + Trip.com 当前可见范围，不代表全网最低、锁价或自动预订。

## D005：Agent 运行框架选型

**状态：已验证；本轮不迁移生产运行框架，PydanticAI 只保留为以后模型调用层的首选试验候选。决定日期：2026-08-23。**

### 结论

TripChord 继续使用当前生产运行方式。不是因为自研天然更好，而是本轮对照只证明五种方案都能承载同一个有界模型工具循环；没有任何候选证明自己能让真实旅行结果更好、让平台查询更快，或在不增加第二套状态的情况下替换现有长任务机制。

如果未来真实主线证明模型调用层已经成为维护阻碍，再先试 **PydanticAI 模型层**：它负责结构化模型输出、工具往返和模型适配，TripChord 仍负责旅行事实、任务身份、偏好、组合优化和最终发布。LangGraph、DBOS、OpenAI Agents SDK、Google ADK、CrewAI、AutoGen 与 Multica 都不进入当前生产依赖。

### 要解决的问题

TripChord 当前同时自研了旅行领域逻辑和大量通用运行能力。框架选型不是为了增加一个热门名词，而是判断能否在不损害真实旅行能力的前提下，减少以下维护负担：

- 模型与只读工具之间的有界循环；
- 结构化输出、模型路由、调用记录与评测；
- 通用任务图、checkpoint、暂停与恢复；
- 长任务重新领取、已完成步骤复用和问题定位。

框架不得拥有旅行事实、组合优化、不可妥协要求、最终发布或用户偏好规则。

### 候选范围

完整比较覆盖当前自研方案和多种主流 Agent 框架。Multica 也被列入，但它本身是管理软件开发 Agent 任务的工具，不是旅行规划框架；把它放进本文，只是为了说明外部 Agent 平台与 TripChord 应该怎样分工。

可执行实验分成两条不同赛道，避免把擅长模型循环的框架与擅长耐久执行的框架混成一个总分：

1. **模型与工具循环**：当前自研、PydanticAI、LangGraph、OpenAI Agents SDK、Google ADK；
2. **长任务与恢复**：当前自研、LangGraph、DBOS。

AutoGen、CrewAI 与 Multica 仍进入事实表，但只有通过架构预筛才编写适配器；不为了凑数量实现已知不匹配的代码。

下面的比较依据 2026-08-23 可查的官方文档与本仓库代码。表里的“适合边界”是结合 TripChord 得出的判断，不是框架官方结论。

| 方案 | 官方能力重点 | 与 TripChord 的重叠 | 适合边界 | 当前主要代价 |
| --- | --- | --- | --- | --- |
| 当前自研 | 类型化模型路由、工具调用、动态任务图、本机任务持久化 | 已覆盖当前完整主链 | 继续作为本轮生产基线 | 通用模型循环、运行记录与恢复代码由项目自行维护 |
| [PydanticAI](https://pydantic.dev/docs/ai/overview/) | 类型化 Agent、工具和输出，多模型适配，测试模型；耐久执行通过 DBOS、Temporal、Prefect、Restate 等组合 | 与现有 Pydantic 领域模型和模型工具循环高度重叠 | 替换模型调用与工具循环，不拥有旅行状态 | 仍需保留 TripChord 任务身份、领域校验和最终发布；耐久能力是另一项选择 |
| [LangGraph](https://langchain-ai.github.io/langgraph/reference/) | 显式状态图、checkpoint、interrupt、durable execution、memory 和 human-in-the-loop | 与动态任务图及长任务恢复重叠 | 只适合真正需要动态语义分支的模型子流程 | 图状态可能与现有任务/报价状态重复；节点重放要求外部查询保持幂等 |

| [AutoGen](https://microsoft.github.io/autogen/) | AgentChat 与事件驱动 Core，强调对话式团队、分布式 Agent 和消息运行时 | 与角色通信和并行执行重叠 | 大规模分布式 Agent 网络或研究型协作 | 当前旅行主链主要是确定性 DAG 与少量模型判断，引入消息运行时会扩大概念面 |
| [CrewAI](https://docs.crewai.com/) | Crew/Task/Process 与 Flow；Flow 支持状态、持久化和恢复 | 同时重叠角色、流程和状态 | 快速搭建角色驱动流程 | 需要把现有角色、任务图和持久化映射进 Crew/Flow，两套抽象的迁移成本高 |
| [Google ADK](https://google.github.io/adk-docs/) | Agent、工具、工作流 Agent、session/state、评测及 A2A；面向 Google Agent Runtime 的部署路径完整 | 与工具、Multi-Agent、会话和评测重叠 | 已采用 Gemini/Vertex/Agent Runtime 或需要 A2A 时 | 对当前本地优先、多模型架构没有独占收益，平台与部署概念较重 |
| [DBOS](https://docs.dbos.dev/python/tutorials/workflow-tutorial) | 普通 Python workflow/step 的持久化执行，完成的 step 恢复后不再执行 | 与长任务 checkpoint、恢复和队列重叠 | 只作为耐久任务执行候选 | 不是 Agent Runtime，不理解旅行领域；仍需解决任务身份、查询幂等与状态归属 |
| [Multica](https://github.com/multica-ai/multica) | 组织多个编码 Agent 完成软件开发任务 | 可以用于管理 TripChord 项目的开发工作，但不解决旅行规划 | 可选的项目开发工具，或把完整 TripChord 当作一项服务调用 | 普通用户不需要安装；不应进入一次旅行规划的内部流程 |

这里有三个不能混淆的“状态”：

- **运行状态**：哪个步骤已完成、哪个模型调用待恢复，可以由通用 runtime 保存；
- **用户偏好**：用户确认过且跨旅行仍稳定的选择，由 TripChord 记忆策略保存；
- **旅行事实**：当前报价、库存、班次、候选和最终方案，只属于当前 TripChord 任务，不能被框架 session 或长期记忆复制成第二份真相。

因此，memory 功能多不代表更适合 TripChord，checkpoint 强也不等于能正确恢复一次有副作用的真实平台查询。

### 候选架构

| 架构 | 形态 | 预期收益 | 核心风险 | 本轮立场 |
| --- | --- | --- | --- | --- |
| A. 全部保持自研 | 现有模型循环、任务图和耐久层不变 | 零迁移风险，领域状态只有一份 | 持续承担通用 runtime 维护 | 生产基线 |
| B. 外部 Agent 工作平台 + TripChord | 让外部平台分别调度 TripChord 内部角色 | 可以统一显示任务进度 | 外部平台必须理解旅行内部流程，并产生两套任务状态 | 否决 |
| C. TripChord + LangGraph | LangGraph 接管模型子图或整条任务图 | 显式分支、checkpoint、interrupt | 与现有任务持久化重叠，迁移面大 | 只保留局部候选 |
| D. TripChord + 单一 Agent SDK | PydanticAI、OpenAI Agents SDK 或 Google ADK 接管模型工具循环，现有任务与领域内核不变 | 删除一部分通用模型适配代码，保留清楚边界 | 真实收益可能小于适配层和升级成本 | 进入同合同实验 |

### 公平实验合同

模型循环实验使用保存的马尔代夫案例包，固定三个场景、相同输入摘要、相同结构化输出和同一工具顺序：

```text
inspect_requirements → inspect_candidate → verify_candidate → Proposal
```

当前自研组真实调用生产 `ModelToolAgent + ScriptedModelClient + ToolRegistry`；PydanticAI、LangGraph、OpenAI Agents SDK 和 Google ADK 分别走各自原生的模型/工具循环。每组使用等价且可重复的预设模型响应脚本，最终结果再由框架外同一个 Pydantic 合同与程序检查器核对。这个实验只比较接入和运行方式，不比较真实模型能力。

长任务实验固定三个保存日期对，但不同系统的失败语义不能假装相同：

- TripChord 生产基线持久化第一个日期对后显式交还 lease，再由新的 repository 实例继续；这不是进程崩溃测试；
- LangGraph 在第二个节点抛错后，用同一 `thread_id` 和 SQLite checkpointer 恢复；
- DBOS 2.x 在同一 workflow 的第一个日期对完成后，让尚未完成的 `crash_once` step 真实终止首进程；第二进程使用同一 system database、workflow 定义和输入，由 `launch()` 原生恢复。实验没有调用 `restart_workflow` 或 `fork_workflow`。

“只换接驳、保留航班和住宿”属于 TripChord 领域重规划，不属于 runtime 胜负。它单独通过生产 `LocalReplanner` 验证，候选框架不能用自己的 state dict 冒充这项能力。

共同采用以下判断标准：

- 同一输入能否产生符合 TripChord 领域合同的输出；
- 中断后是否重复查询已经完成的来源或日期；
- 是否形成第二套旅行状态；
- 是否保留修改未涉及的组件；
- 模型调用、工具调用、耗时与隐式重试；
- tracing、可测试性和当前维护状态；
- 能删除多少通用自研代码，以及新增多少框架适配代码。

### 最终选择

#### 生产架构

采用“稳定领域内核 + 可替换模型端口 + 单一耐久状态 + MCP 外观”的分层 Hybrid，但当前每层仍由已有实现承担：

```text
原生 UI / Claude Code / 标准 MCP 客户端 / 其他宿主（需单独验证）
                        │
                 Typed API / MCP
                        │
        TripChord 任务身份与长任务协调（唯一运行状态）
                        │
      来源查询 ─→ 报价归一 ─→ 组合优化 ─→ 最终校验
                        │
            可替换的模型判断端口（当前自研）
                        │
         PydanticAI 仅作为未来有界试验候选
```

这意味着本轮最终选择是 **保持生产实现，不引入框架依赖**。PydanticAI 赢得的是“最值得继续验证的模型层候选”，不是“已经迁移的生产 Runtime”。

#### 为什么暂不选择其他方案

- **LangGraph**：真实证明了 checkpoint 恢复，但 TripChord 已经有任务、lease 和日期对持久化；整链迁移会先增加第二套状态，尚未证明能删除更多代码或改善旅行结果。
- **OpenAI Agents SDK**：工具、结构化输出和 tracing 完整，离线闭环也通过；但 TripChord 当前需要多模型路由，它相对 PydanticAI 没有表现出额外收益。
- **Google ADK**：原生闭环通过，A2A、评测和 Google 部署能力丰富；当前产品是本地优先且不绑定 Gemini/Vertex，这些优势不是现阶段瓶颈。
- **AutoGen / CrewAI**：强项是对话团队或角色/流程抽象；TripChord 的主体是确定性查询与组合求解，映射成本大于已知收益。
- **DBOS**：这次真实双进程实验已经证明完成的 step 不会因原生恢复而重复；但它只解决耐久执行。若接入生产，仍要把现有任务身份、lease、日期对唯一性和领域重规划迁移到同一权威状态，而不是在旁边再增加一套 system database。本轮没有证明这项迁移能删除更多代码或改善旅行结果。
- **Multica**：它适合管理软件开发 Agent，不是旅行规划 Runtime。它可以把完整 TripChord 当作一项服务调用，但不进入一次旅行规划内部。

#### 现有代码怎样处理

**保留：**

- `domain/`、`planning/`、`providers/` 的旅行领域对象、来源适配、组合优化、Pareto、最终校验和局部重规划；
- 用户偏好与实时旅行事实的隔离规则；
- typed job API、任务身份、lease、日期对唯一性与当前持久化表；
- `ContextEngine` 的最小上下文投影和 `ToolRegistry` 的工具合同；
- 框架无关的运行轨迹与最终发布检查。

**只在 PydanticAI 真实试点通过后合并或删除：**

- 把 `ModelToolAgent` 与 `StructuredLiveModelAgent` 的共同模型循环收敛到一个 `ReasoningRuntime` 端口；
- 用 PydanticAI adapter 替换重复的结构化输出解析、工具往返和一部分 provider glue；
- 只有新 adapter 覆盖现有模型路由与运行记录后，才删除被完全替代的通用代码。

本轮不删除任何生产代码，也不让框架接管领域状态。

#### 未来试验与停止条件

1. **已完成：离线同合同实验。** 确认五种模型 Runtime 都能承载相同工具闭环，并保留失败边界。
2. **当前不继续迁移。** 先完成跨平台准确报价、个性化选择和完整日期提速；框架试验不能抢占这些产品结果。
3. **触发后只做单角色 PydanticAI 试验。** 选择一个确实需要语义判断、但不拥有旅行事实的角色，在同一模型、同一提示、同一工具与同一输出合同下对比；不改来源查询和任务持久化。
4. **只有明确胜出才局部迁移。** 新路径必须保持端到端结果、不增加来源重复查询、不产生第二套状态，并且删除的通用代码多于新增适配与维护代码。
5. **长任务框架另行决定。** 只有真实进程终止或重启表明 LangGraph 或 DBOS 能替换而非叠加现有任务机制时，才重新开启耐久层迁移。

若 PydanticAI 不能在真实模型 A/B 中改善可维护性或至少保持调用与耗时，它就停止在实验目录，生产继续使用当前实现。若未来动态语义分支成为主要复杂度，而不是平台查询和组合优化，才重新评估 LangGraph。

#### 面试叙事

适合高级 Agent / 产品工程面试的主线不是“我用了很多框架”，而是：

> TripChord 把一次复杂旅行拆成可核对的真实来源、确定性组合优化和少量必须由模型判断的用户取舍。价格、日期和可行性不交给 LLM；当前已经能跳过一部分无价值模型调用，下一步让更多角色按真实问题触发。我用同一旅行合同实跑了五种模型运行方式，并单独比较长任务恢复；结果支持保留领域内核与单一状态源，把 PydanticAI 仅作为未来可替换模型层的候选，而不是为了框架标签重写系统。

这个叙事允许面试官继续追问：为什么这不是 shortest path、怎样构造 Pareto 候选、什么时候触发额外 Agent、为什么 checkpoint 不能代替旅行状态、为什么局部修改是受约束重新求解，以及什么实验才足以推翻当前选型。

## D006：旅行组合优化内核

**状态：2.0 已保留固定结构快路径，并由 D007 扩展为范围受控的复杂旅行内核。决定日期：2026-08-23。**

### 问题定义

TripChord 要解决的不是“让模型写一份看起来合理的攻略”，而是从本次实际取得的航班、住宿和接驳中找出能够一起成立的完整行程。一个候选方案可以表示为：

```text
方案 = 出行日期 + 航班 + 住宿/房型 + 去程接驳 + 返程接驳
```

候选首先要满足日期、人数、房间、行李、入住、转机和接驳衔接等不可妥协的要求；剩余方案再按用户本次在意的价格、时间、舒适度、位置与便利性形成 Pareto 集合。只有进入这个集合的方案，才需要模型理解用户没有写成公式的取舍。

形式上，先由程序构造可行集合 `F`，其中每个 `x = (date, flight, room, outbound_transfer, return_transfer)` 都满足全部约束；再求非支配集合：

```text
P = { x ∈ F | 不存在 y ∈ F 在所有已比较维度都不差，并且至少一项更好 }
```

所有人的总费用、总耗时、中转次数等可计算维度直接来自归一结果；住宿品质、位置便利性等语义维度只能由有来源输入的模型给出结构化评价。用户偏好清楚时，从 `P` 中按其优先顺序或明确交换关系选 `x*`，而不是把所有人塞进同一个永久权重公式。

### 算法选择

当前单目的地往返旅行是规模受控的离散组合选择，不是天然的 shortest path 问题。最合适的主链是：

1. 程序枚举合法日期，并对来源查询结果做稳定身份与所有人的人民币总费用归一；
2. 尽早用不可妥协的要求剪枝，避免生成明显不可能的组合；
3. 在剩余候选上做精确组合与 Pareto dominance 过滤；
4. 按已确认的用户偏好选择一份方案；偏好不足时，从同一 Pareto 集合抽取省钱、均衡和体验三个代表点；
5. 最后由程序复算完整行程，模型不能把不可行候选“解释成可行”。

候选数量继续扩大时，优先加入 branch-and-bound 或 CP-SAT，而不是先把当前固定结构强行改写成图。D006 当时把“多城市、多段交通和可替换活动”列为重新评估条件；新的产品定位已经明确包含这些问题，因此目标架构由 D007 接续。现有固定结构组合器仍保留为简单场景快路径。

### 增量重规划

“只换酒店、保留航班”不是模型凭语言承诺，而是一个受约束的重新求解：把未受影响的航班与接驳固定为已选变量，只重新查询和选择住宿，再检查完整行程。若修改影响日期、目的地、同行构成或衔接关系，则扩大受影响集合；无法保持原组件时必须明确说明，不能静默改掉。

这使局部修改成为完整规划能力的一部分，而不是项目主命题。主命题仍然是：理解每位用户真正想要的旅行，从可比较的真实候选中找到最合适的完整方案。

### LLM 不参与的决定

下列问题必须由确定性程序或来源事实回答：日期是否合法、所有人的总费用、币种换算口径、税费是否已包含、两个报价是否为同一产品、库存与班次是否仍有效、接驳能否赶上、候选是否满足不可妥协的要求，以及最终结果是否可以发布。

LLM 只处理自然语言偏好、住宿品质与位置的语义判断、Pareto 候选之间无法被固定规则替代的取舍，以及面向用户的解释。这个边界在更换任何 Agent 框架后都必须保留。

### 重新评估条件

- 真实任务出现多城市、多段活动与路径依赖，现有组合器无法在查询预算内完成；
- CP-SAT 或 RCSP 在同一真实候选集上显著减少搜索时间，同时不降低可解释性和增量修改能力；
- 当前 Pareto 规则无法稳定表达用户实际取舍，并有真实失败案例证明需要新的目标建模。

## D007：面向复杂自由行的通用领域内核

**状态：已实现并完成七轮范围受控场景验证；更广泛组合仍按兼容路线扩展。决定日期：2026-08-25。**

### 问题

TripChord 的定位不再只覆盖“一个出发地到一个目的地的机票、酒店和接驳套餐”。2.0 已在范围受控场景覆盖多城市、异地进出、不同地点出发后汇合、固定活动、亲子或长辈同行、部分人员提前离开等需求；更广泛的组合仍需逐项扩展验证。

如果继续给 `PackageIntent`、`PackageCandidateKind` 和马尔代夫地点枚举增加分支，每一种旅行结构都会复制查询、组合、修改和验证逻辑。反过来，一次性用万能图或万能求解器替换现有真实链，也会牺牲已经验证的能力，并把尚未证明的抽象当成产品进度。

### 决定

采用**渐进兼容的领域内核**：

1. 用类型化的 `TravelIntent` 表达同行者、地点、时间窗、固定活动、不能妥协的条件和个人取舍；
2. 用 `RequirementGraph`、`OfferGraph` 和 `PlanGraph` 分别表达需求依赖、本次来源时空网络和最终方案；图是领域视图，不是 Agent 执行图，也不要求图数据库；
3. 用 `OfferCatalog + PriceContract` 统一交通、住宿、接驳、活动和不可拆整包，明确每个价格覆盖的人员、组件、日期、税费和币种；
4. 由 `PlanningCompiler` 识别问题结构：当前固定套餐走现有精确组合快路径；有限候选下的城市顺序、房间、活动和人员分合流优先用 CP-SAT；RCSP 只在同一数据基准证明有必要后加入；
5. 可行方案先通过程序复算，再形成 Pareto 集合；模型只处理需求歧义、来源语义冲突、候选取舍和被当前行程触发的专业旅行风险；
6. 当前 `PackagePlanner` 先实现统一 `PlanSolver` 接口，通过适配器接入新合同，不进行大爆炸重写。

完整对象、算法和角色边界见[复杂自由行目标架构](target-architecture.md)。

### 为什么不选择其他方案

| 方案 | 结论 |
| --- | --- |
| 继续扩充现有套餐对象 | 会把每种城市结构和人员组合变成中央分支，无法形成长期可扩展的旅行内核 |
| 一次性重写为通用图求解器 | 没有兼容证据，容易丢失现有价格、来源和修改语义 |
| 所有复杂问题都使用 CP-SAT | 简单问题承担不必要成本；未查询的全球旅行空间也不能直接交给有限约束求解器 |
| 先自研 RCSP | 路径资源约束不适合共享房价、套票和多人分组；必须先有同一 OfferGraph 基准证明收益 |
| 让多个 Agent 自由协商方案 | 不能证明总价、人员连续性和可行性，且会产生第二套旅行状态 |
| 为此迁移 LangGraph 等 Runtime | 当前主要缺口在旅行领域模型和求解，不在通用执行框架；迁移不能改善最终旅行答案 |

### 依据与证据边界

当前仓库已经有通用 `TripSpec`、`ItineraryItem`、依赖分析、CP-SAT 活动调度、Pareto 处理、来源记录和局部重规划，也有能够运行的单目的地套餐链。因此兼容迁移有实际起点。

多城市、异地进出、分组同行、共享价格合同和活动组合已经作为统一端到端能力进入七轮验收；D007 的证据和范围见 [2.0 公共验收](v2.0-acceptance.md)。架构验证仍不能代替未覆盖来源的真实平台结果。

### 验证与停止条件

七轮已用固定来源回放和范围受控当前来源运行三种结构，而不是把一次耗时数天的全窗口查询当作架构证明：

1. 当前单目的地灵活日期往返；
2. 多城市异地进出并包含固定时间活动；
3. 两地出发后汇合、部分活动不全员参加且部分人提前离开。

三种场景共用同一个需求合同、来源目录、求解入口、最终复算和行程卡。每位同行者全程连续，共享价格只计算一次；酒店失效后保留航班和固定活动，只替换受影响组件。小型库存与暴力枚举结果一致。逐轮结果见 [2.0 公共验收](v2.0-acceptance.md)。

如果新增旅行结构仍需要复制中央工作流，说明领域模型需要修正；如果 CP-SAT 成为平台查询之外的新瓶颈，再用同一 OfferGraph 比较 RCSP 或分解求解；如果新合同无法等价复现当前马尔代夫结果，停止迁移并保留现有生产路径。

### 影响

- 保留来源记录、币种、产品身份、查询任务、Pareto、CP-SAT 经验、偏好记忆、版本差异和最终复算；
- 用适配器逐步把 `PackageIntent`、往返航班、地点枚举、`PackageInventory` 和 `TravelPackageCandidate` 映射到新合同；
- 等新旧等价、多城和分组场景都通过后，才删除马尔代夫专用枚举和固定整团往返假设；
- Multi-Agent 改为由确定性 Need Router 按歧义、冲突、取舍和特殊风险触发，日期与平台继续作为普通并行任务；
- 对外 API/MCP 只暴露完整规划、进度、修改和结果，不暴露内部角色。
