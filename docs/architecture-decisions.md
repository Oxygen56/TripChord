# TripChord 架构决策记录

这份文档记录会改变 TripChord 产品职责、核心算法、Agent 分工或长期维护方式的重要决定。它不是开发流水账，也不以“采用了多少框架”为成果。每项决定都要说明：解决什么问题、选择了什么、为什么、哪些方案被否决、当前证据支持到哪一层，以及什么新事实会迫使我们重新评估。

目前的架构结论是：TripChord 保持独立的旅行 Agent 与 Decision Engine；旅行事实和组合优化不交给通用 Agent 框架；Multi-Agent 按真实任务动态运行；用户偏好决定什么叫“最好”；外部 Harness 通过 MCP 调用完整 TripChord；生产 Runtime 暂不迁移，PydanticAI 只作为下一次模型层试点的首选候选。

- 改变 TripChord 对用户承诺的最终结果；
- 改变 LLM、确定性程序和真实来源之间的责任边界；
- 引入或移除会长期影响核心运行方式的框架；

- **已确认**：方向已经确定，但实现或真实验证尚未完成；
- **已验证**：已经有可复现运行支持该决定；

## D001：TripChord 是独立的垂直旅行 Agent

**状态：已确认；现有旅行内核已有历史真实来源回放支持。决定日期：2026-08-23。**

### 决定

TripChord 定位为面向复杂自由行规划的垂直 Agent 与 Decision Engine，不定位为通用 Multi-Agent 框架。它必须能够脱离 Multica、Oh My Pi、DeepSeek Harness 或其他宿主，独立完成一次旅行规划。

通用框架可以替换模型调用、任务图、checkpoint 或 tracing，但不能接管以下旅行事实与决定：

- 日期与同行人数；
- 航班、住宿、房型和接驳的稳定身份；
- 人民币同行总价及其可比性；
- 明确条件与行程衔接；
- 组合候选、Pareto 集合和最终方案；
- 修改影响范围以及未受影响部分的保留；
- 稳定用户偏好与实时价格、库存之间的隔离。

这些能力继续由 `domain/`、`planning/`、`providers/` 和偏好规则共同拥有。框架状态只能保存运行进度和领域对象引用，不能成为第二套报价或最终方案事实源。

### 为什么

TripChord 的差异化价值来自旅行问题本身：把真实来源中不可直接比较的产品变成完整可行方案，再根据当前用户的取舍给出答案。调度器、模型工具循环和 checkpoint 很重要，但它们可以替换；旅行语义和最终决策合同不能外包。

### 否决的方向

- 把 TripChord 改造成 Multica 内部的一组 Issue 或 Coding Agent 任务；
- 让外部 Harness 分别调度 TripChord 内部角色并拼接最终答案；
- 把实时报价、任务终态或最终方案复制到宿主会话中作为另一份权威状态；
- 为了展示框架而重写已经能独立验证的旅行领域函数。

### TripChord 与 Multica 的合理关系

| 方案 | 判断 | 原因 |
| --- | --- | --- |
| 完全独立运行 | **保留，且是默认形态** | 用户无需安装 Multica；TripChord 的产品、数据和任务生命周期完整 |
| 部分复用 Multica | **可选** | Multica 可以管理 TripChord 项目的开发、评测或定时运维任务，但不介入一次旅行规划 |
| Multica 作为 TripChord 内部 Runtime | **否决** | Multica 当前运行的是外部 Coding Agent CLI 和 Issue 生命周期，不是进程内旅行工作流；会增加跨系统状态和故障面 |
| TripChord 作为 Multica 上层领域应用 | **有条件可行** | Multica 可以把完整 TripChord 服务当作一个 HTTP/MCP 能力调用，但不能分别调度内部角色或拼装报价 |
| 合并两个项目的 Runtime 代码 | **否决** | 两者问题定义不同；共享代码会让通用控制面与旅行领域状态互相污染 |

因此最合理的长期关系是“独立产品 + 可选外层调用”，不是父子框架，也不是共用数据库。

### 重开条件

只有当外部运行时能在同一真实旅行流程中保持全部领域合同，同时显著减少 TripChord 自研通用代码，而且不引入第二套状态时，才重新考虑更深的依赖关系。

## D002：用户目标决定什么叫最佳方案

**状态：已确认；多种默认答案仍是后续产品实现，不是当前 1.0 已有能力。决定日期：2026-08-23。**

### 决定

TripChord 不把“最低价格”写成所有用户共用的固定目标，也不使用一个不可解释的全局加权分数。

一次需求先被整理为：

1. 不可妥协的条件；
2. 当前旅行中的个人优先顺序；
3. 可以接受的交换关系，例如为了直飞、酒店品质或节省时间最多愿意多花多少。

用户已经表达清楚偏好时，系统只给一份个性化最佳方案。用户没有提供足够偏好时，系统从同一个可行 Pareto 候选集合中给出三份代表性答案：

- **省钱优先**：满足基本品质要求后，人民币同行总价更低；
- **综合均衡**：价格、时间、住宿品质与接驳便利性之间的代表性平衡点；
- **体验优先**：优先舒适度、位置和便利性，价格作为次要比较条件。

“体验优先”不等于无限预算，也不表示已经覆盖全网；它只在本次实际取得且可比较的候选中成立。

### 执行边界

- LLM 理解自然语言中的偏好与交换关系；
- 确定性程序生成合法日期、计算金额、过滤不可行项并形成 Pareto 集合；
- 三种答案复用同一轮来源查询和同一候选集合，不能各自重新跑一遍完整搜索；
- 当前请求始终可以覆盖长期偏好；只有用户确认过的稳定偏好可以写入记忆；
- 实时价格、库存和班次不能进入长期偏好记忆。

### 验证要求

实现后需要证明：同一批来源只查询一次；三种模式返回彼此有意义且不重复的代表方案；用户给出明确偏好时能稳定收敛为一份答案；选择一种模式后不会自动把本次偶然选择冒充长期偏好。

## D003：Multi-Agent 按任务需要动态运行

**状态：已确认；现有角色仍需通过真实模型消融决定保留、合并或确定性化。决定日期：2026-08-23。**

### 决定

Agent 数量不是目标。一个角色只有在需要独立的上下文、工具权限、模型判断或失败边界时才保留为 Agent；日期生成、金额计算、产品身份、硬条件校验和最终发布不能因为换了名称就被包装成 Agent。

目标角色包括：

- **需求与偏好 Agent**：理解当前请求和可接受的取舍；
- **平台搜索 Agent**：只在网页需要自主导航和判断时使用，可按平台或日期范围动态并行；
- **体验评价 Agent**：处理位置、品质、舒适度等不完全规则化的信息；
- **决策 Agent**：只在 Pareto 候选之间存在真实价值取舍时运行；
- **审查 Agent**：只在来源冲突、低置信度或高代价选择时触发并提出结构化异议；
- **表达与记忆 Agent**：生成中文说明并提出可能值得记住的偏好，不能自行确认长期记忆。

API 查询、日期枚举、并发调度、报价归一、组合优化、硬校验、增量重规划和发布仍是确定性组件。

一个日期组合只是待查询的工作项，不是一个 Agent。程序先生成完整合法日期空间，再由有界并发池分配查询；只有某个平台确实需要自主浏览、识别页面和处理交互时，才临时启动对应的平台搜索 Agent。

这里的 Skill、Tool 和 Plugin 不是同一层：

- **Skill** 是可版本化的旅行判断方法，例如怎样识别“位置方便”或怎样解释转机代价；它只提供方法，不保存实时价格；
- **Tool** 是模型能调用的类型化函数，例如读取已确认需求、读取候选或请求确定性校验；调用结果可以被程序记录和拒绝；
- **Plugin / MCP** 是 TripChord 与外部 Harness 的安装和通信方式，不进入内部旅行推理。

| 模型角色 | 只接收的上下文 | 允许使用的能力 | 明确不能做什么 |
| --- | --- | --- | --- |
| 需求与偏好 | 当前请求、已确认的适用偏好 | 偏好读取、偏好候选提取 | 写入价格/库存，或自行确认长期记忆 |
| 平台搜索 | 一个来源与一组已分配日期 | 对应 provider/浏览器查询工具 | 改日期全集、比较全局最优或发布结果 |
| 体验评价 | 归一后的住宿/航班语义和来源片段 | 位置、舒适度、权益判断 Skill | 改金额、库存或可行性 |
| 决策 | 已通过校验的 Pareto 候选与用户优先顺序 | 有界候选比较 | 搜索新报价或接受不可行候选 |
| 条件审查 | 最终候选、来源引用和校验结果 | 只读反例与缺口检查 | 直接修改方案或用投票覆盖程序检查 |
| 表达与记忆 | 已发布方案与可说明的取舍 | 中文说明、偏好候选建议 | 新增任何来源事实或自动写入记忆 |

### 关于 debate、voting 和 Multi-Critic

默认不采用模型投票、持续辩论或 BFT-inspired consensus。多个相近模型读取相同来源时，不具备独立副本系统所要求的故障假设；多数赞成也不能证明日期、价格或库存正确。

审查 Agent 的输出是可以核对的反例、风险或缺失证据，不是一张票。事实异议交给确定性检查，主观取舍才交给用户目标和模型判断。只有受控实验能证明多审查者在某类高风险语义问题上带来稳定收益时，才允许条件触发。

### 验证要求

对每个模型角色记录：是否改变最终有效方案、是否减少人工澄清或错误、增加多少模型调用和耗时。无法证明边际价值的角色应合并、按需触发或改成确定性函数。

### 当前对照结果

仓库的[单 Agent / Multi-Agent 公平基准](benchmark-agent-architectures.md)让两种架构使用同一套 12 个任务、同一 scripted model、同一只读工具和相同总预算。2026-08-23 的可复现结果如下：

| 指标 | 单 Agent | Multi-Agent |
| --- | ---: | ---: |
| 有效方案率 | 100% | 100% |
| 需要修改时的成功率 | 100% | 100% |
| 平均模型调用 | 4.25 | 10.25 |
| 平均工具调用 | 4.25 | 10.25 |
| 平均 token | 799 | 1,927 |

机器可读结果见 [`benchmarks/results/agent-architecture-v1.json`](../benchmarks/results/agent-architecture-v1.json)。这次对照证明了两套执行路径和统计口径可复现，也证明固定展开所有角色会增加调用；因为使用的是 scripted model，它不能证明真实模型下单 Agent 或 Multi-Agent 谁的答案更好。

因此当前决定不是删除 Multi-Agent，而是取消“每次都跑完整团队”：平台搜索可以按来源和日期动态并行；需求理解、体验判断、取舍和条件审查只在输入真正需要时实例化。要让某个角色进入默认主链，必须再用真实模型和未见旅行任务证明它带来的答案提升大于新增耗时与调用。

## D004：通过 MCP 接入其他 Agent Harness

**状态：已确认；接口尚未实现。决定日期：2026-08-23。**

### 决定

TripChord 对 Oh My Pi、DeepSeek Harness 以及其他 Agent 宿主采用 MCP-first 边界：宿主负责接收用户请求和展示结果，TripChord 负责完整旅行规划和最终决策。

选择这个边界不是假设宿主能力：[Oh My Pi 已提供原生 MCP 配置](https://github.com/can1357/oh-my-pi/blob/main/docs/mcp-config.md)，[DeepSeek Harness 也已有 MCP client plugin](https://github.com/deepseek-ai/deepseek-harness/tree/master/packages/mcp/mcp-client)。DeepSeek Harness 当前仍标为 developer preview，所以 TripChord 不依赖它不稳定的内部 Cordis API；MCP 是两边都能保持独立演进的更窄接口。

推荐的公共操作保持粗粒度：

- `create_plan`：创建规划任务并返回任务编号；
- `get_plan`：查询进度或取得最终结构化方案；
- `modify_plan`：按新要求生成新版本和变化说明。

真实平台规划可能持续数分钟，不能把它包装成一个一直阻塞的工具调用。MCP 只是现有异步任务 API 的稳定外观，不新增第二套任务状态。

### 组合方式

```text
Oh My Pi / DeepSeek Harness / 其他宿主
                  │
             Skill + MCP Client
                  │
          TripChord MCP Facade
                  │
          TripChord Typed Job API
                  │
     旅行 Decision Engine 与真实来源适配器
```

共享 Skill 只说明何时调用、如何表达需求以及如何忠实展示结果。价格计算、约束校验和最终选择不能依赖 Skill 提示词。

Oh My Pi Extension 或 DeepSeek Cordis Plugin 只在需要宿主专属命令、进度卡片或轨迹入口时增加，而且内部仍然调用同一个 MCP 接口。TripChord 不导入宿主代码、不共享数据库，也不把内部每个 Agent 暴露成单独工具。

### 验证要求

同一个任务通过 TripChord 原生入口和 MCP 入口运行时，应产生相同任务身份、相同最终方案和相同修改差异；MCP 入口不得增加一次完整重复搜索。

## D005：Agent Runtime 框架选型

**状态：已验证；本轮不迁移生产 Runtime，PydanticAI 作为下一次模型层试点的首选候选。决定日期：2026-08-23。**

### 结论

TripChord 继续使用当前生产 Runtime。不是因为自研天然更好，而是本轮对照只证明五种方案都能承载同一个有界模型工具循环；没有任何候选证明自己能让真实旅行结果更好、让平台查询更快，或在不增加第二套状态的情况下替换现有长任务机制。

如果下一阶段要替换一层，先只试 **PydanticAI 模型层**：它负责结构化模型输出、工具往返和模型适配，TripChord 仍负责旅行事实、任务身份、偏好、组合优化和最终发布。LangGraph、DBOS、OpenAI Agents SDK、Google ADK、CrewAI、AutoGen 与 Multica 都不进入当前生产依赖。

### 要解决的问题

TripChord 当前同时自研了旅行领域逻辑和大量通用运行能力。框架选型不是为了增加一个热门名词，而是判断能否在不损害真实旅行能力的前提下，减少以下维护负担：

- 模型与只读工具之间的有界循环；
- 结构化输出、模型路由、调用记录与评测；
- 通用任务图、checkpoint、暂停与恢复；
- 长任务重新领取、已完成步骤复用和问题定位。

框架不得拥有旅行事实、组合优化、硬条件、最终发布或用户偏好规则。

### 候选范围

完整事实比较覆盖：当前自研、LangGraph、OpenAI Agents SDK、AutoGen、CrewAI、Google ADK、PydanticAI、DBOS 和 Multica。

可执行实验分成两条不同赛道，避免把擅长模型循环的框架与擅长耐久执行的框架混成一个总分：

1. **模型与工具循环**：当前自研、PydanticAI、LangGraph、OpenAI Agents SDK、Google ADK；
2. **长任务与恢复**：当前自研、LangGraph、DBOS。

AutoGen、CrewAI 与 Multica 仍进入事实表，但只有通过架构预筛才编写适配器；不为了凑数量实现已知不匹配的代码。

### 框架能力与 TripChord 的真实重叠

下面的比较依据 2026-08-23 可查的官方文档与本仓库代码。表里的“适合边界”是结合 TripChord 得出的判断，不是框架官方结论。

| 方案 | 官方能力重点 | 与 TripChord 的重叠 | 适合边界 | 当前主要代价 |
| --- | --- | --- | --- | --- |
| 当前自研 | 类型化模型路由、工具调用、动态任务图、本机任务持久化 | 已覆盖当前完整主链 | 继续作为本轮生产基线 | 通用模型循环、运行记录与恢复代码由项目自行维护 |
| [PydanticAI](https://pydantic.dev/docs/ai/overview/) | 类型化 Agent、工具和输出，多模型适配，测试模型；耐久执行通过 DBOS、Temporal、Prefect、Restate 等组合 | 与现有 Pydantic 领域模型和模型工具循环高度重叠 | 替换模型调用与工具循环，不拥有旅行状态 | 仍需保留 TripChord 任务身份、领域校验和最终发布；耐久能力是另一项选择 |
| [LangGraph](https://langchain-ai.github.io/langgraph/reference/) | 显式状态图、checkpoint、interrupt、durable execution、memory 和 human-in-the-loop | 与动态任务图及长任务恢复重叠 | 只适合真正需要动态语义分支的模型子流程 | 图状态可能与现有任务/报价状态重复；节点重放要求外部查询保持幂等 |
| [OpenAI Agents SDK](https://openai.github.io/openai-agents-python/) | Agent、Runner、函数工具、handoff、guardrail、session 和 tracing，并允许自定义 Model | 与模型工具循环、角色交接和追踪重叠 | OpenAI 为主要模型平台时的模型层候选 | 不能替代长任务控制与旅行状态；对现有多模型路由的收益需实测 |
| [AutoGen](https://microsoft.github.io/autogen/) | AgentChat 与事件驱动 Core，强调对话式团队、分布式 Agent 和消息运行时 | 与角色通信和并行执行重叠 | 大规模分布式 Agent 网络或研究型协作 | 当前旅行主链主要是确定性 DAG 与少量模型判断，引入消息运行时会扩大概念面 |
| [CrewAI](https://docs.crewai.com/) | Crew/Task/Process 与 Flow；Flow 支持状态、持久化和恢复 | 同时重叠角色、流程和状态 | 快速搭建角色驱动流程 | 需要把现有角色、任务图和持久化映射进 Crew/Flow，两套抽象的迁移成本高 |
| [Google ADK](https://google.github.io/adk-docs/) | Agent、工具、工作流 Agent、session/state、评测及 A2A；面向 Google Agent Runtime 的部署路径完整 | 与工具、Multi-Agent、会话和评测重叠 | 已采用 Gemini/Vertex/Agent Runtime 或需要 A2A 时 | 对当前本地优先、多模型架构没有独占收益，平台与部署概念较重 |
| [DBOS](https://docs.dbos.dev/python/tutorials/workflow-tutorial) | 普通 Python workflow/step 的持久化执行，完成的 step 恢复后不再执行 | 与长任务 checkpoint、恢复和队列重叠 | 只作为耐久任务执行候选 | 不是 Agent Runtime，不理解旅行领域；仍需解决任务身份、查询幂等与状态归属 |
| [Multica](https://github.com/multica-ai/multica) | 管理外部 Coding Agent CLI 的任务、运行时、进度、团队和 Skill | 与项目级任务派发、监控和复用重叠，不与旅行规划内核重叠 | 可选的外层开发/运维控制面，或把 TripChord 当一个完整能力调用 | 把它放进单次旅行规划会把业务任务误建模为 Coding Agent Issue，并增加跨系统状态 |

这里有三个不能混淆的“状态”：

- **运行状态**：哪个步骤已完成、哪个模型调用待恢复，可以由通用 runtime 保存；
- **用户偏好**：用户确认过且跨旅行仍稳定的选择，由 TripChord 记忆策略保存；
- **旅行事实**：当前报价、库存、班次、候选和最终方案，只属于当前 TripChord 任务，不能被框架 session 或长期记忆复制成第二份真相。

因此，memory 功能多不代表更适合 TripChord，checkpoint 强也不等于能正确恢复一次有副作用的真实平台查询。

### 候选架构

| 架构 | 形态 | 预期收益 | 核心风险 | 本轮立场 |
| --- | --- | --- | --- | --- |
| A. 全部保持自研 | 现有模型循环、任务图和耐久层不变 | 零迁移风险，领域状态只有一份 | 持续承担通用 runtime 维护 | 生产基线 |
| B. TripChord + Multica | Multica 直接调度 TripChord 内部 Agent | 统一外部任务管理界面 | 产品边界错误、跨系统状态、旅行流程被编码任务语义污染 | 否决 |
| C. TripChord + LangGraph | LangGraph 接管模型子图或整条任务图 | 显式分支、checkpoint、interrupt | 与现有任务持久化重叠，迁移面大 | 只保留局部候选 |
| D. TripChord + 单一 Agent SDK | PydanticAI、OpenAI Agents SDK 或 Google ADK 接管模型工具循环，现有任务与领域内核不变 | 删除一部分通用模型适配代码，保留清楚边界 | 真实收益可能小于适配层和升级成本 | 进入同合同实验 |
| E. 分层 Hybrid | Agent SDK 只管模型循环；TripChord 管旅行内核；现有耐久层或 DBOS 单独管长任务；MCP 对外 | 每层只解决自己擅长的问题，可独立替换 | 需要严守状态归属，不能一次引入全部组件 | 首选目标形态，但必须分步证明 |

### 公平实验合同

模型循环实验使用保存的马尔代夫案例包，固定三个场景、相同输入摘要、相同结构化输出和同一工具顺序：

```text
inspect_requirements → inspect_candidate → verify_candidate → Proposal
```

当前自研组真实调用生产 `ModelToolAgent + ScriptedModelClient + ToolRegistry`；PydanticAI、LangGraph、OpenAI Agents SDK 和 Google ADK 分别走各自原生的模型/工具循环。每组使用等价且可重复的 scripted response plan，最终结果再由框架外同一个 Pydantic 合同与确定性审计器检查。这个实验只比较接入和运行语义，不比较真实模型智力。

长任务实验固定三个保存日期对，但不同系统的失败语义不能假装相同：

- TripChord 生产基线持久化第一个日期对后显式交还 lease，再由新的 repository 实例继续；这不是进程崩溃测试；
- LangGraph 在第二个节点抛错后，用同一 `thread_id` 和 SQLite checkpointer 恢复；
- DBOS 2.x 在同一 workflow 的第一个日期对完成后，让尚未完成的 `crash_once` step 真实终止首进程；第二进程使用同一 system database、workflow 定义和输入，由 `launch()` 原生恢复。实验没有调用 `restart_workflow` 或 `fork_workflow`。

“只换接驳、保留航班和住宿”属于 TripChord 领域重规划，不属于 runtime 胜负。它单独通过生产 `LocalReplanner` 验证，候选框架不能用自己的 state dict 冒充这项能力。

共同采用以下判断标准：

- 同一输入能否产生符合 TripChord 领域合同的输出；
- 中断后是否重复查询已经完成的来源或日期；
- 是否形成第二套旅行状态；
- 是否保留修改未涉及的组件；
- 模型调用、工具调用、耗时与隐式重试；
- tracing、可测试性和当前维护状态；
- 能删除多少通用自研代码，以及新增多少框架适配代码。

### 最终选择

#### 生产架构

采用“稳定领域内核 + 可替换模型端口 + 单一耐久状态 + MCP 外观”的分层 Hybrid，但当前每层仍由已有实现承担：

```text
原生 UI / Oh My Pi / DeepSeek Harness / 其他宿主
                        │
                 Typed API / MCP
                        │
        TripChord 任务身份与长任务协调（唯一运行状态）
                        │
      来源查询 ─→ 报价归一 ─→ 组合优化 ─→ 最终校验
                        │
            可替换的模型判断端口（当前自研）
                        │
         PydanticAI 仅作为下一次有界试点候选
```

这意味着本轮最终选择是 **保持生产实现，不引入框架依赖**。PydanticAI 赢得的是“最值得继续验证的模型层候选”，不是“已经迁移的生产 Runtime”。

#### 为什么暂不选择其他方案

- **LangGraph**：真实证明了 checkpoint 恢复，但 TripChord 已经有任务、lease 和日期对持久化；整链迁移会先增加第二套状态，尚未证明能删除更多代码或改善旅行结果。
- **OpenAI Agents SDK**：工具、结构化输出和 tracing 完整，离线闭环也通过；但 TripChord 当前需要多模型路由，它相对 PydanticAI 没有表现出额外收益。
- **Google ADK**：原生闭环通过，A2A、评测和 Google 部署能力丰富；当前产品是本地优先且不绑定 Gemini/Vertex，这些优势不是现阶段瓶颈。
- **AutoGen / CrewAI**：强项是对话团队或角色/流程抽象；TripChord 的主体是确定性查询与组合求解，映射成本大于已知收益。
- **DBOS**：这次真实双进程实验已经证明完成的 step 不会因原生恢复而重复；但它只解决耐久执行。若接入生产，仍要把现有任务身份、lease、日期对唯一性和领域重规划迁移到同一权威状态，而不是在旁边再增加一套 system database。本轮没有证明这项迁移能删除更多代码或改善旅行结果。
- **Multica**：最合理的关系是外层开发/运维控制面，或将来调用完整 TripChord 服务，不进入一次旅行规划内部。

#### 现有代码怎样处理

**保留：**

- `domain/`、`planning/`、`providers/` 的旅行领域对象、来源适配、组合优化、Pareto、最终校验和局部重规划；
- 用户偏好与实时旅行事实的隔离规则；
- typed job API、任务身份、lease、日期对唯一性与当前持久化表；
- `ContextEngine` 的最小上下文投影和 `ToolRegistry` 的工具合同；
- 框架无关的运行轨迹与最终发布检查。

**只在 PydanticAI 真实试点通过后合并或删除：**

- 把 `ModelToolAgent` 与 `StructuredLiveModelAgent` 的共同模型循环收敛到一个 `ReasoningRuntime` 端口；
- 用 PydanticAI adapter 替换重复的结构化输出解析、工具往返和一部分 provider glue；
- 只有新 adapter 覆盖现有模型路由与运行记录后，才删除被完全替代的通用代码。

本轮不删除任何生产代码，也不让框架接管领域状态。

#### 分阶段迁移与停止条件

1. **已完成：离线同合同实验。** 确认五种模型 Runtime 都能承载相同工具闭环，并保留失败边界。
2. **下一步：单角色 PydanticAI pilot。** 选择一个确实需要语义判断、但不拥有旅行事实的角色，在同一模型、同一提示、同一工具与同一输出合同下 A/B；不改来源查询和任务持久化。
3. **真实模型比较。** 用未见旅行任务记录答案有效率、模型/工具调用、token、耗时、provider 切换成本和实际可删除的自研代码。没有模型密钥时不把 scripted 结果当替代品。
4. **只有明确胜出才局部迁移。** 新路径必须保持 1.0 端到端结果、不增加来源重复查询、不产生第二套状态，并且删除的通用代码多于新增适配与维护代码。
5. **长任务框架另行决定。** 只有真实进程终止/重启实验表明 LangGraph 或 DBOS 能替换而非叠加现有 job/lease/pair 机制时，才重新开启耐久层迁移。

若 PydanticAI 不能在真实模型 A/B 中改善可维护性或至少保持调用与耗时，它就停止在实验目录，生产继续使用当前实现。若未来动态语义分支成为主要复杂度，而不是平台查询和组合优化，才重新评估 LangGraph。

#### 面试叙事

适合高级 Agent / 产品工程面试的主线不是“我用了很多框架”，而是：

> TripChord 把一次复杂旅行拆成可核对的真实来源、确定性组合优化和少量必须由模型判断的用户取舍。Multi-Agent 角色按问题动态实例化，价格、日期和可行性不交给 LLM。我用同一旅行合同实跑了五种模型 Runtime，并单独比较长任务恢复；结果支持保留领域内核与单一状态源，把 PydanticAI 仅作为可替换模型层的下一候选，而不是为了框架标签重写系统。

这个叙事允许面试官继续追问：为什么这不是 shortest path、怎样构造 Pareto 候选、什么时候触发额外 Agent、为什么 checkpoint 不能代替旅行状态、为什么局部修改是受约束重新求解，以及什么实验才足以推翻当前选型。

## D006：旅行组合优化内核

**状态：已确认；当前离散候选规划与局部修改已有实现，通用求解器尚未引入。决定日期：2026-08-23。**

### 问题定义

TripChord 要解决的不是“让模型写一份看起来合理的攻略”，而是从本次实际取得的航班、住宿和接驳中找出能够一起成立的完整行程。一个候选方案可以表示为：

```text
方案 = 出行日期 + 航班 + 住宿/房型 + 去程接驳 + 返程接驳
```

候选首先要满足日期、人数、房间、行李、入住、转机和接驳衔接等不可妥协的要求；剩余方案再按用户本次在意的价格、时间、舒适度、位置与便利性形成 Pareto 集合。只有进入这个集合的方案，才需要模型理解用户没有写成公式的取舍。

形式上，先由程序构造可行集合 `F`，其中每个 `x = (date, flight, room, outbound_transfer, return_transfer)` 都满足全部约束；再求非支配集合：

```text
P = { x ∈ F | 不存在 y ∈ F 在所有已比较维度都不差，并且至少一项更好 }
```

同行总价、总耗时、中转次数等可计算维度直接来自归一结果；住宿品质、位置便利性等语义维度只能由有来源输入的模型给出结构化评价。用户偏好清楚时，从 `P` 中按其优先顺序或明确交换关系选 `x*`，而不是把所有人塞进同一个永久权重公式。

### 算法选择

当前单目的地往返旅行是规模受控的离散组合选择，不是天然的 shortest path 问题。最合适的主链是：

1. 程序枚举合法日期，并对来源查询结果做稳定身份与人民币同行总价归一；
2. 尽早用不可妥协的要求剪枝，避免生成明显不可能的组合；
3. 在剩余候选上做精确组合与 Pareto dominance 过滤；
4. 按已确认的用户偏好选择一份方案；偏好不足时，从同一 Pareto 集合抽取省钱、均衡和体验三个代表点；
5. 最后由程序复算完整行程，模型不能把不可行候选“解释成可行”。

候选数量继续扩大时，优先加入 branch-and-bound 或 CP-SAT，而不是先把问题改写成图。只有产品进入多城市、多段交通和可替换活动的 time-expanded network 后，constrained shortest path 或 RCSP 才会成为更自然的表达。普通动态规划只在状态维度能够被严格限制时使用，否则会把价格、时间、品质和权益组合成不可控状态空间。

### 增量重规划

“只换酒店、保留航班”不是模型凭语言承诺，而是一个受约束的重新求解：把未受影响的航班与接驳固定为已选变量，只重新查询和选择住宿，再检查完整行程。若修改影响日期、目的地、同行构成或衔接关系，则扩大受影响集合；无法保持原组件时必须明确说明，不能静默改掉。

这使局部修改成为完整规划能力的一部分，而不是项目主命题。主命题仍然是：理解每位用户真正想要的旅行，从可比较的真实候选中找到最合适的完整方案。

### LLM 不参与的决定

下列问题必须由确定性程序或来源事实回答：日期是否合法、同行总价、币种换算口径、税费是否已包含、两个报价是否为同一产品、库存与班次是否仍有效、接驳能否赶上、候选是否满足不可妥协的要求，以及最终结果是否可以发布。

LLM 只处理自然语言偏好、住宿品质与位置的语义判断、Pareto 候选之间无法被固定规则替代的取舍，以及面向用户的解释。这个边界在更换任何 Agent 框架后都必须保留。

### 重新评估条件

- 真实任务出现多城市、多段活动与路径依赖，现有组合器无法在查询预算内完成；
- CP-SAT 或 RCSP 在同一真实候选集上显著减少搜索时间，同时不降低可解释性和增量修改能力；
- 当前 Pareto 规则无法稳定表达用户实际取舍，并有真实失败案例证明需要新的目标建模。
